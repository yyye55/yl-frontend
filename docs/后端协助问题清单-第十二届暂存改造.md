## 二、P0：必须优先修

### P0-1　新增页会把内容写进被驳回的正式报名（数据覆盖）

**症状**：某校有一份被驳回的报名 R1。用户点「修改报名」进入编辑（此时后端建了一条
`report_id = R1` 的草稿），随后又切去「赛事报名」新增页填一份全新的表。结局是：

- 新增页填的内容**没有变成新报名**；
- 被驳回的 **R1 被整份替换**成新表的内容；
- `Report` 表条数仍然是 1，**从条数上完全看不出问题**。

**根因**：`apps/core/report_drafts.py:229` `create_or_get_draft()` 的筛选条件是

```python
draft = ReportDraft.objects.select_for_update().filter(
    user_id=user.id, scope=scope, state=ReportDraft.STATE_EDITING   # ← 没有 report_id
).order_by("id").first()
if draft is None:
    return ReportDraft.objects.create(...)
draft.payload = payload        # ← 无条件覆盖
```

它按用户 + 渠道找「唯一一条编辑中的草稿」，**完全不看 `report_id`**。而「新增报名」
和「修改被驳回的报名」是两种业务意图，却共用同一条草稿行。

**证据**（`probe_rejected` test_10，实际输出）：

```
OK   edit-draft 草稿绑定 R1
FAIL 新增页拿到的是新草稿（report_id 应为空）   期望 None  实际 '1'
FAIL 新增页没有复用编辑中的草稿                 期望 True  实际 False
FAIL R1 的内容未被新增页覆盖                    期望 True  实际 False
     （Report 数=1，R1 名称='这其实是一份全新的报名'，提交返回 report_id=1）
```

**建议改法**（二选一，推荐第 1 种）：

1. `create_or_get_draft` 增加 `report_id` 维度：新增页只认 `report_id IS NULL` 的草稿，
   `edit-draft` 只认 `report_id = R` 的草稿。两条业务线彻底分开。
2. 若要保持「一个用户同时只有一条编辑中草稿」，则新增页在发现已有草稿**绑定了
   `report_id`** 时必须报错，而不是静默覆盖。

> 附带提醒：`ReportDraft.report_id` 已经有索引（`models.py:233`），按它查询不会有性能问题。

### P0-2　乐团简介 255 字上限卡死整条报名链路（无法提交）

**症状**：用户在「乐团简介」里写 256～300 字 → 点暂存 → 弹「desc 长度不能超过 255」；
点提交同样失败。**用户没有任何办法继续**，只能删字。

**三个数字互相对不上**：

| 位置 | 文件:行 | 值 |
|---|---|---|
| 红头文件（两处原文「300字以内乐团简介」） | — | **300** |
| 前端输入框 | `yl-frontend/src/components/elementary/OrchestraForm.vue:219` | `maxlength="300"` |
| 数据库列 | `yilinbeihou/apps/core/models.py:178` | `max_length=1000` |
| **后端校验** | `yilinbeihou/apps/core/report_drafts.py:88` `def _string(value, field, required=False, maximum=255)` | **255** ← 卡在这里 |

`:159` 那一行调 `_string(value, field)` 时**没有传 `maximum`**，于是一律落到默认的 255。

**证据**（`probe_more` 11 / 11b，实际输出）：

```
【11】255 字 → 200
  FAIL 256 字 → 应当也能存下      期望 200  实际 400（msg='desc 长度不能超过 255'）
  FAIL 300 字（前端上限）→ 应当能存下   实际 400
【11b】首次暂存 HTTP 期望 200 实际 400  ⇒ 草稿根本没建起来（Report 数=0）
```

**建议改法**：给 `desc` 单独上限，与 DB 列对齐：

```python
_LIMITS = {"desc": 1000}          # 与 Report.desc max_length 对齐
...
result[field] = _string(value, field, maximum=_LIMITS.get(field, 255))
```

**前端为什么不能自己修**：把 `maxlength` 改成 255 能消除报错，但那等于**前端擅自把
红头文件的 300 字砍成 255**，是拿产品规则去迁就实现缺陷。前端保留 300 不动。

### P0-3　同一学校可产生第二条正式报名（重复报名）

**症状**：某校已提交报名 R1，用户重新进入报名页再填一份并提交 → 库里出现 R2。
违反红头文件「每所学校限报一支队伍，且只能参加一个组别」。

**根因**：走草稿链路的提交最终调用 `apps/core/report_drafts.py:206`
`create_report_from_submission()`，它的全部内容就是：

```python
def create_report_from_submission(user, submission, scope=None):
    ok, stored = store_people(user, list(submission.people))
    if not ok:
        raise InvalidSubmission(stored)
    report = Report.objects.create(user_id=user.id, **submission.report)   # ← 无任何数量校验
    attach_report_people(report.id, stored)
    return report
```

对比老的直建路径 `apps/api/views.py:109` `create_report()`，那里**至少有**省级的 8 队限制：

```python
if province and Report.objects.filter(user_id=user.id).count() >= 8:
    return response(failure("目前您的单位已超报送限制,无法再继续进行报送!"))
```

也就是说：**新的草稿提交路径比老的直建路径更宽松**，把仅有的那道限制也绕过去了。

**证据**（`probe_rejected` test_09）：

```
OK   第二次 POST 草稿 HTTP
OK   新草稿未关联原报名
OK   第二次提交 HTTP
FAIL Report 表仍只有 1 条      期望 1  实际 2
     （实际 Report 数=2；第二条 report_id=2，首条=1）
```

**这与 `BACKEND_ISSUES.md` 的 BE-02 是同一条**，但 BE-02 描述的是 `create_report`，
**没有覆盖草稿提交路径**。请按本文档补充处理。

**建议改法**：`create_report_from_submission` 提交前检查
`Report.objects.filter(user_id=user.id, deleted_at__isnull=True).exists()`，
命中则返回 409 + 明确文案。**最终仍建议在数据库层加唯一约束**（并发下应用层检查有竞态）。

### P0-4　导出的官方附件2：**长号被并进「其他」栏**，栏目次序也与红头文件不符

> 这一条与暂存改造无关，是**导出功能本来就有**的缺陷。放在 P0 是因为它污染的是
> **那张要打印、盖章、扫描回传的官方报名表**——附件2 是报名的法定凭证。

**红头文件原文（两处，均逐字核对）**：

- 三、报名要求（二）乐团要求：
  > 管乐团应包含铜管（含圆号、小号、**长号**、次中音号和大号等）、木管（含长笛、单簧管、萨克斯管等）以及打击乐器……
- 附件2「正式队员名单」栏，**长号有独立栏目**，且次序固定：

  > 短笛：　长笛：　单簧管：　低音单簧管：　中音萨克斯：　次中音萨克斯：
  > **上低音萨克斯：　双簧管：　大管：　小号：　长号：　圆号：　上低音号：　大号：　打击乐：　低音大提琴：　其他：**

**后端两个乐器表，一个对、一个错**：

| 位置 | 内容 | 项数 | 与附件2 比对 |
|---|---|---|---|
| `apps/api/export_services.py:49-53` `INSTRUMENTS` | 短笛…**长号**…其他 | **17** | ✅ **逐字逐序完全一致** |
| `apps/api/registration_form.py:12-17` `FORM_INSTRUMENTS` | 短笛…小号、**上低音萨克斯**、圆号…其他 | **16** | ❌ **缺「长号」**；且**「上低音萨克斯」位置错**（被排到「小号」之后，红头文件里它在「次中音萨克斯」之后） |

`registration_form.py` 的模块 docstring 与 `:110` 的注释**把这个漏项写成了既定口径**：

```python
# 模块 docstring：乐器名经 _instrument_bucket 归一到官方表格的 16 个栏目
# :12  # 官方表格的 16 个乐器栏目（含上低音萨克斯、无长号；表外乐器并入"其他"）
FORM_INSTRUMENTS = (...)                      # 16 项，含上低音萨克斯、无长号
# :110
bucket = "其他"  # 表外乐器（如长号）统一并入"其他"栏
```

**后果链**（`form_context()` → `_instrument_bucket()` → `:110` 兜底）：

1. 报名库里 `Person.instrument` 存的是 `"长号"`（前端下拉确有长号，见下）；
2. `_instrument_bucket("长号")` 返回 `"长号"`，但 `instrument_names` 这个 dict
   **是按 `FORM_INSTRUMENTS` 建的，没有「长号」这个键**；
3. 于是 `:110` 的 `bucket = "其他"` 兜底生效 → **这名长号队员被印在「其他」栏下**。

**为什么这是 P0 而不是 UI 问题**：`_instrument_bucket` 只做「归一」，判据是**乐器名是否
在官方栏目里**；长号**在**官方栏目里，是被后端自己漏掉的。所以这不是「表外乐器归到其他」
的正常兜底，而是**把表内乐器当成表外**——3 名长号学生在一张盖章上传的报名表上被登记为
「其他乐器」。组委会按表核对编制时会直接读到错误信息。

**前端侧是对的，不要动**：
`yl-frontend/src/components/elementary/PersonTable.vue:124-141` 的 17 个 `el-option`
**逐字、逐序**与附件2 一致（含长号，长号在「小号」之后）。前端下拉选得出长号，
后端打印不出来——两侧对同一条规则给出了不同答案，**以后端为准去改前端会让错的那一侧变成两处**。

**建议改法**：把 `FORM_INSTRUMENTS` 与 `export_services.INSTRUMENTS` **合并成一处常量**
（两处逐字相同后自然就对了），或直接令 `FORM_INSTRUMENTS = INSTRUMENTS`。顺序按附件2：

```python
FORM_INSTRUMENTS = (
    "短笛", "长笛", "单簧管", "低音单簧管", "中音萨克斯", "次中音萨克斯",
    "上低音萨克斯", "双簧管", "大管", "小号", "长号", "圆号", "上低音号", "大号",
    "打击乐", "低音大提琴", "其他",
)   # 17 项，与 export_services.INSTRUMENTS 逐字一致
```

改完后 `:110` 的 `"其他"` 兜底**应当保留**——它对真正的表外乐器（如「次中音号」，
红头文件（二）里用的是这个词，而附件2 栏目写的是「上低音号」）仍是必要的。
只需在测试里断言 `_instrument_bucket("长号") == "长号"`，防止再次被误并。

## 三、P1：核心功能异常

### P1-1　重复进入「修改报名」会冲掉用户已暂存的修改

**症状**：用户被驳回后点「修改报名」，改到一半（已自动暂存），中途切走再点一次
「修改报名」→ 之前改的内容**全没了**，表单变回正式报名里的旧内容。

**根因**：`apps/api/views.py:871` `_edit_draft()` 每次进入都**无条件**重建草稿：

```python
draft = ReportDraft.objects.select_for_update().filter(
    report_id=report.id, user_id=request.auth.id, scope=scope).first()
payload = encode_payload(build_payload_from_report(report))   # ← 每次都从正式报名重建
if draft is None:
    draft = ReportDraft.objects.create(..., payload=payload, ...)
else:
    draft.payload = payload                                   # ← 覆盖掉用户改的内容
    draft.version = F("version") + 1
```

**证据**（`probe_rejected` test_06，实际输出）：

```
FAIL 第二次 edit-draft 后内容仍是用户改的
     期望 '用户改了一半'   实际 '探针曲目'
     依据 重复点击「修改报名」不该用旧报名内容覆盖用户已暂存的编辑
OK   version 只增不减
```

**建议改法**：`_edit_draft` 找到**已存在且 `state=EDITING`** 的草稿时，**直接返回它**，
不要用 `build_payload_from_report` 重建。只在草稿不存在（或已提交）时才从正式报名播种。

> 前端已做的兜底：编辑页现在也有 60 秒本地镜像（`localStorage`），重进页面时会把
> 用户最后看到的内容盖回去。**这只是兜底**——它救不了换设备、清缓存、清 localStorage 的场景，
> 而且服务端那份确实已经被冲掉了。请仍按上面的建议修后端。

### P1-2　`GET /api/export/data` 跨校数据泄漏（建议与 P0 同批修）

**症状**：**任何学校账号**（`type=0`）调用该接口，都能拿到**全市所有学校**的报名数据。

**根因**：`apps/api/views.py:394`

```python
@api.get("/export/data", auth=auth)
def export_data(request):
    qs = Report.objects.all().order_by("id")        # ← 没有 user 过滤
    if request.GET.get("group"):                    # ← group 是组别过滤，不是归属过滤
        qs = qs.filter(group=request.GET["group"])
    write_log(request.auth, 6, "导出报送数据")
    return reports_export_response(qs, "数据导出.xlsx")
```

对比同文件的 `/export/report`（`:376`）与 `/export/person`（`:385`），它们都写了
`filter(user_id=request.auth.id, ...)`；`/export/data` 既没有这个过滤，**也没有 `role_error()`**。

**证据**（`probe_export` 12r，含正向对照，排除「解析写错了」的可能）：

```
OK   HTTP 200（校级账号可访问）        （格式=csv，500 字节）
OK   能看到自己学校的数据               ← 正向对照，证明解析方式没错
FAIL 看不到别校数据      期望 False  实际 True
OK   组委会账号（type=2）能看到学校的报名
FAIL 带 group 过滤时依然不该看到别校数据
```

> 探针里是 csv 而不是 xlsx，是因为本地 `.venv` 未装 `openpyxl`，走了
> `export_services.py:339` 的 `except ImportError:` 兜底分支。
> 生产环境 `requirements.txt:7` 声明了 `openpyxl==3.1.5`，导出的是真 xlsx——
> **但这不影响结论**，泄漏发生在查询集构造阶段，与导出格式无关。

**按等级表这属于「权限」，列在 P1；但它是一次数据安全事故，建议与 P0 同批修。**

**建议改法**：与 `/export/report` 对齐——`qs = qs.filter(user_id=request.auth.id)`，
并补上 `role_error(request, expected)`；组委会/管理员需要全量导出的话，
应另开一个明确鉴权的管理端接口。

### P1-3　统计页数字与导出表口径不一致

同一个用户看到的「总数」和导出出来的报名表**条数对不上**，因为两处对**状态**的处理不同：

| 位置 | 代码 | 口径 |
|---|---|---|
| `views.py:700` / `:704` / `:709`（`scoped_total`，即各首页统计） | `qs.count()` | **全部状态**，含已驳回(-1)、未填写(-2) |
| `views.py:196`（`stats`） | `qs.count()` | **全部状态** |
| `views.py:376` / `:385`（`/export/report`、`/export/person`） | `filter(status__gte=0)` | **排除**已驳回(-1)、未填写(-2) |

**症状**：某校有 1 条正常 + 1 条被驳回，首页显示「总数 2」，导出的报名表只有 1 页。
用户会认为导出漏了数据。

**证据**：源码逐行核对（上表每格都标了文件:行）。这一条没有写成探针，因为它是纯粹的
口径定义问题，不是行为异常——**修之前需要先确定哪个口径是对的**。

**建议**：请后端明确「各首页展示的『总数』是否应当含已驳回/未填写」，

### P1-4　用餐预约：**整条功能是断的**（前端无控件 / 后端不记人数 / 格数与红头文件不符）

> 这一条同样是**导出/表单本身的缺陷**，不是暂存改造引入的。列在 P1 是因为它不阻塞提交，
> 但红头文件明确要求的功能在系统里**完全不可用**。

**红头文件附件2 原文**（用餐预约栏 + 其下的备注 1）：

> 用餐预约
> 　11月21日午餐　11月21日晚餐　11月22日午餐　11月22日晚餐
> 备注：1. 如果需在成都理工大学食堂购票用餐，**请备注时间并在对应位置写上就餐人数**。

三处问题，逐条列清：

**（1）格子数：后端 6 格，红头文件 4 格**

```python
# apps/api/registration_form.py:19-20
MEALS = ("11月20日午餐", "11月20日晚餐", "11月21日午餐", "11月21日晚餐",
         "11月22日午餐", "11月22日晚餐")
MEAL_HINTS = (("20", "午"), ("20", "晚"), ("21", "午"), ("21", "晚"),
              ("22", "午"), ("22", "晚"))
```

红头文件里**没有 11月20日的用餐格**——对照上报时间「2026年11月20日8:00—12:00」，
20 日是**报到日**，组委会不安排食堂购票用餐。多出的两列会让打印出来的报名表
与官方空白表式样不一致；学校若在 20 日两格填了，组委会也没有对应的安排可兑现。

**（2）后端只画 `√`，红头文件要的是「就餐人数」**

```python
# apps/api/registration_form.py:56-79  _meal_cells()
if text.isdigit() and 0 <= int(text) < len(MEALS):
    cells[int(text)] = "√"        # ← 无论传进来什么，格子里只会出现 √
```

`dinner_reservation` 被当作**「选了/没选」的布尔集合**，而红头文件要求填的是**人数**。
更麻烦的是它的匹配是**宽松包含**：

```python
if text == label or all(part in text for part in MEAL_HINTS[index]):
```

即 `"11月21日午餐2人"` 里同时含 `"21"` 和 `"午"` → 命中并写 `√`，**「2人」被静默丢弃**。
想保留人数只能故意传入匹配不上的字符串，让它落进 `leftovers` 再由
`form_context()` 追加到备注栏——**靠兜底路径承载正常语义，是脆的**：
后端哪天把匹配改宽，这些字符串就会被吞成 `√`，人数无声消失。

**（3）前端模板里根本没有这个控件**

`OrchestraForm.vue:395` 已注明：`dinner_reservation:[]` 在表单初值里，但**模板中没有任何控件绑定它**。
`src/` 全目录 grep `dinner_reservation` 只有 8 处，全部是：dist 初值、类型注释、
`draftPayload` 的往返透传——**没有一处是 UI**。

也就是说：一所学校需要 11月21日午餐 20 份，**在系统里没有任何地方可以填**。

---

**⚠️ 给后端的接口陷阱（改前端之前必须先定这个）**

`_meal_cells` 同时接受三种写法，**下标语义绑死在 `MEALS` 的 6 格顺序上**：

| 写法 | 例 | 落到哪一格 |
|---|---|---|
| 下标 `0-5` | `"0"` | `MEALS[0]` = **11月20日午餐** |
| 完整文案 | `"11月21日午餐"` | 命中同名格 |
| 简写 | `"21午"` | 由 `MEAL_HINTS` 定位 |

所以**如果前端按红头文件的 4 格做 UI、并发送下标 `0-3`，四顿饭会全部落到 11月20日**
（`0→20午`、`1→20晚`、`2→21午`、`3→21晚`）——**四顿全错，且表格上看起来完全正常**。
这是一个不会报错、只会静默错位的数据错误。

在 `MEALS` 改成 4 格（或改成「人数数组」）**之前，前端不得按 `0-3` 下标发送**。

**建议的最终契约**（供后端采纳，前端照此实现）：

```
dinner_reservation: [ {"meal": "11月21日午餐", "count": 20}, ... ]
或退一步（改动最小）：保持字符串数组，元素为**完整文案**，人数单独一个键：
dinner_reservation: ["11月21日午餐", ...]
dinner_count:      {"11月21日午餐": 20, ...}
```

同时 `MEALS` 收敛为红头文件的 4 格，`_meal_cells` 写**人数**而非 `√`，
并停用「下标」与「宽松包含」两种写法（前者是上面那个陷阱，后者会吞掉人数）。
存量 `dinner_reservation` 数据的迁移口径请一并给出——库里可能已有历史值。

**为什么前端本轮不擅自把控件补上**（这是一次有意的取舍，不是漏做）：

1. 补了也只能发「选没选」，**红头文件要的人数照样丢**——等于做出一个**看起来能用、
   实际丢数据**的控件，比没有控件更坏（用户会以为填过了）。
2. 按 4 格发下标会把四顿饭静默错位到 20 日（见上表）。
3. 现在没有任何学校能用这个字段，**存量数据为零**，改契约的代价此刻最低；
   等前端铺上控件、收到一批「只有 √ 没有人数」的数据之后再改，代价高得多。

所以这一条**故意留空**，等后端把契约定下来，前端一次性做对。

## 四、P2：健壮性与可维护性

### P2-1　`report_draft` 表无唯一约束，并发下会产生两条「编辑中」草稿

`apps/core/models.py:206-234` 的 `ReportDraft` 只有两个 `Index`，**没有任何
`unique_together` / `UniqueConstraint`**。而 `create_or_get_draft` 的
`select_for_update()` **锁不住一行还不存在的记录**（幻读）——两个并发 POST 会各自
`draft is None` 然后各建一条。

**建议**：加 `UniqueConstraint(fields=["user_id", "scope", "report_id"], ...)`
（`report_id` 为 NULL 的场景需按数据库类型确认 NULL 语义），或用
`get_or_create` + 重试。

### P2-2　请求体是合法 JSON 但不是对象 → 500 而非 400

`apps/core/services.py:27` `parse_body()` 对合法 JSON 原样返回，不校验类型。
于是 `POST /api/school/report/drafts` 带 body `"abc"` 时：

```
File "apps/api/views.py", line 762, in _draft_payload_body
    return data.get("payload", data)
AttributeError: 'str' object has no attribute 'get'
```

**证据**（`probe_json`，实际异常栈如上）：字符串 / 数组 / 数字三种 body 都触发。
生产环境（`DEBUG=False`）下这是一个 **500**，会污染错误日志并给客户端一个无意义的响应。

**建议**：`parse_body` 里加 `if not isinstance(value, dict): return request.POST.dict()`
或直接抛 400。

### P2-3　`edit-draft` / 驳回重提零测试覆盖

`tests/test_report_drafts.py` 共 **6 个用例**，覆盖：编解码、字段白名单、暂存期人员非必填、
版本冲突 + 跨用户隔离、提交幂等、scope 隔离。**没有任何一条覆盖 `edit-draft` 或驳回重提。**

本轮 4 个最严重的缺陷（P0-1、P0-3、P1-1，以及 P0-2 的 255 上限）**全部落在这一块无人看守的区域**。
建议把这 4 条按本文档的复现步骤直接固化成回归测试。

### P2-4　草稿接口不写 `write_log`

`:775` / `:790` / `:803` / `:815` / `:840` / `:861` / `:897` 这些草稿相关分支都没有
`write_log(...)`，而 `create_report`（`views.py:131`）、`export_report`（`:377`）等都有。
草稿是用户实际发生的数据写入，出问题时按日志查不到任何痕迹。

### P2-5　本地 sqlite 下 `select_for_update()` 是空操作

项目所有并发假设都建立在 `select_for_update()` 上，但 sqlite 不支持行级锁，
本地开发/测试环境**根本测不出并发问题**。这不是代码缺陷，是**验证盲区**——
建议后端在上线前用 PostgreSQL（或至少在生产同构环境）跑一次并发压测。
