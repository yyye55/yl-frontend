但用 curl 手发一个**不带** `old_password` 的请求仍能改掉密码：这道校验挡得住
"界面上的操作者"，挡不住"绕过界面的调用方"。第六节第 3 条的预期据此已过期。

## 一、背景

### 1.1 这是怎么冒出来的

第十二届前端一度把自助改密整个删掉了：弹窗（右上角「修改信息」）里只剩一个
「重置密码」按钮，点一下把密码恢复成默认口令 `scylb@2026`。
当时的理由是"全站口径统一为恢复默认口令，留着自选密码等于开后门"。

这个判断只对了一半 —— 口径统一指的是**管理员替他人重置**时的语义；
用户给**自己**设密码本来就不该受这条约束。删掉之后的实际后果是：

- 密码只剩两个来源：建号时管理员填的初始密码，以及各处写死的默认口令；
- **没被管理员单独设过密码的账号会永远停在 `scylb@2026`**；
- 登录页那句「密码为初始密码，请登录系统后在右上角的[修改信息]中修改密码」
  照着做只会把它重置回同一个默认口令 —— 那句话当时是失效的。

现已把「当前密码 / 新密码 / 确认新密码」加回弹窗，与「重置为默认密码」并存。
登录页那条提醒也随之重新成立。

### 1.2 为什么现在需要后端配合

改密码本身走 `PUT /api/user`（`user_update`），后端**已经支持**：

```python
# apps/api/views.py:337
if data.get("password"):
    user.set_password(data["password"])
```

`user_update` 是"发什么就设成什么"，所以**改密码今天就能生效，不依赖这次改造**。
缺的只有一件事：**没有人核对过 `old_password`**。
（→ 这一件已经在 `8d6b105` 补上了，本节其余内容为背景。）

> 注意与另外两处区分：`/admin/user`、`/committee/user` 的「重置密码」走的是
> `user_update_admin`（`apps/api/views.py:680`），那里被改成了
> `if "password" in data: user.set_password(RESET_PASSWORD_DEFAULT)` ——
> **请求体里的值被忽略，一律重置为默认口令**。本次请求与那两处无关，请不要顺手改动它们。

## 二、需要后端做的改动

### 2.1 改动位置

`PUT /api/user` → `user_update`（`apps/api/views.py:325`），仅 **337 行那一处**。

### 2.2 建议改法

```python
    for key in ("username", "nickname", "description", "tel", "leader"):
        if key in data:
            setattr(user, key, data[key])

    if data.get("password"):
        # 【新增】改密码必须先核对原密码。
        # 判据用 data.get("old_password")："没带这个键"与"带了个错值"要区分开 ——
        # 只有前者才放行（兼容旧调用方），后者一律拒绝。
        if not verify_user_password(user, data.get("old_password") or ""):
            return response(failure("当前密码不正确"))
        user.set_password(data["password"])

    user.save()
```

> **【实际落地的写法与上面不同】** 后端 `8d6b105` 用的是**兼容写法**：
>
> ```python
> if "old_password" in data and not verify_user_password(user, data.get("old_password") or ""):
>     return response(failure("当前密码不正确"))
> ```
>
> 差别只有一处，但方向明确：**"不带这个键"由"拒绝"改成了"放行"**。
> 这正是上面 `data.get("old_password") or ""` 那句注释的取舍点 ——
> 后端选了兼容旧调用方那一侧。上面的代码块保留为**建议原文**，不要再照它改。

### 2.3 三个必须注意的点

**① 必须用 `verify_user_password`（`apps/core/services.py:469`），不要用 `user.check_password()`。**

这个 helper 是 `check_password()` 的替代品，专门处理 Laravel 遗留的
`$2y$` bcrypt 摘要（`views.py:291` 的登录接口用的就是它）。
存量账号里有一批是 `$2y$` 开头的哈希，`check_password()` 对它们一律返回 `False` ——
如果这里用 `check_password`，**这批账号会连自己的正确密码都过不了校验，直接被锁在门外**。
这正是这个 helper 当初被写出来的原因，别绕开它。

**② `return` 必须发生在 `user.save()` 之前 —— 现在的写法已经满足，请保持。**

上面的 `setattr` 只改了内存对象，`user.save()` 在最后一行。
提前 `return response(failure(...))` 不会落库，**不会出现"密码没改成、昵称却被改了"的半截写入**。

反过来说：原密码不对时，**昵称等资料字段也一并不生效**，这是**预期行为**，不要"顺手修正"成
"先存资料、再校验密码" —— 前端在收到 `code != 0` 时会保留弹窗并提示，用户改对原密码后
点一次确定即可，两件事同时提交、同时落库或同时不落库，语义最干净。

**③ 判据是 `data.get("password")` 存在，不是 `old_password` 存在。**

只改昵称（不带 `password`）的请求走的是老路径，与本次改动无关，不受影响。

### 2.4 响应约定（前端已按此实现，无需再沟通）

返回 `failure("当前密码不正确")` 即可（`code = 1`，`msg` 为提示语）。
前端 `submit()` 里已有分支：

```js
if (res.code !== 0) {
  ElMessage.warning(res.msg)   // ← 直接展示 msg，不关弹窗
  return
}
```

所以**文案由后端决定**。若你们想改成「原密码有误」之类的措辞，改 `msg` 即可，前端不用动。

## 四、评估过、但没采用的替代方案

供你们判断"是不是非改后端不可"时参考。

### 4.1 前端先用 `POST /api/login` 验一次原密码

技术上可行（登录接口就是校验口令的），且有真实拦截效果。**没采用**，两个原因：

- `login` 每次调用都会 `PersonalAccessToken.issue()`（`views.py:292`）
  并 `write_log(user, 4, "用户登录")`，而它**不吊销任何既有 token**。
  于是每改一次密码，库里就多一条永远不会被使用的 token 记录，
  日志里多一条并不属实的「用户登录」。审计日志被污染，代价比省下的 6 行代码大。
- 这是把登录接口当口令校验器用，属于绕过契约；后端一旦调整登录侧逻辑
  （例如加图形验证码、加登录频率限制），这条路会静默失效。

### 4.2 前端探测后端是否支持 `old_password`

例如发一个只带 `id` 和错 `old_password`、不带 `password` 的请求，
用返回码反推后端有没有实现。**没采用**：多一次请求、多一条日志，
而且把一个本该显式声明的契约变成了靠副作用猜。放在交接文档里说清楚更直接。

### 4.3 干脆不要在界面上收原密码

**没采用**：这是与使用者确认后否掉的方案。改密码不收原密码不符合常规做法，
且会话未锁屏时他人可代改密码。

## 五、影响面

### 5.1 只影响自助改密这一个入口

- `/admin/user`、`/committee/user` 的「重置密码」走 `user_update_admin`，**不受影响**；
- 只改资料（不带 `password`）的请求，**不受影响**；
- 登录接口 `POST /api/login`，**不受影响**。

### 5.2 存量数据

存量账号的密码哈希格式不一（Django PBKDF2 与 Laravel `$2y$` bcrypt 混存）。
如 2.3 ① 所述，这**正是必须用 `verify_user_password` 的原因**，
否则存量账号会被大面积挡住。建议上线前用一个 `$2y$` 开头的账号实测一次。

### 5.3 可选项（本次不要求）：改密码后吊销该用户的其它 token

改了密码，其它设备上的会话仍然有效 —— 语义上是"密码换了但会话还开着"。
现状是前端在改完密码后主动调 `POST /api/logout` 注销**自己这一次**的 token，
所以当前设备是干净的，其它设备不会。

如果要做，建议单独评估：这会同时影响 `user_update_admin` 的重置路径，
且要考虑"用户在多端登录时被另一端点一下重置密码就全部掉线"是否符合业务预期。
**本次不要求，请不要顺手加上。**

## 六、验收方式

后端上线后，按下列三条验证即可：

1. **正确原密码**：填对原密码 + 合法新密码 → 返回 `code = 0`；
   用该账号**旧密码**登录失败、**新密码**登录成功。
2. **错误原密码**：故意填错原密码 → 返回 `code = 1`、`msg` 为提示语；
   **旧密码仍然可以登录**（这一条最关键 —— 验证没有发生半截写入）；
   同时确认这一次请求里带的 `nickname` 等资料字段**也没有被写进库**（符合 2.3 ②）。
3. ~~**不带 `old_password`**（用 curl 直接发 `{"id":..,"password":".."}`）：应被**拒绝**。~~
   **本条的预期已过期。** 后端实际落地时取了兼容写法（判据 `"old_password" in data`），
   所以这条请求**会被放行**、密码直接被改掉 —— 这是**有意**的选择，不是漏判。
   改后的验收口径应为：不带该键 → `code = 0`、密码确实被改。
   （若日后要收紧成"缺失即拒绝"，删掉 `"old_password" in data and ` 即可，
   前端无需同步改动。）

   > 原判断依据（历史）：`data.get("old_password") or ""` 里的 `or ""` 会让"缺失"与"错值"
   > 走同一条拒绝分支。这个取舍点现在由后端拍板成了兼容侧。

## 七、~~不做会怎样~~（已失效的历史段落）

> **本节的窗口期已经关闭**（后端 `8d6b105` 上线，「当前密码」一栏现在是真正生效的校验）。
> 段落保留在此，只作为"当时为什么催这件事"的记录，**不要再当作现状引用**。

当时的中间状态是：前端**已经**在收原密码并发出去，界面上看不出任何异常 ——

- 用户会以为"系统核对过我的原密码"；
- 实际上后端忽略 `old_password`，**填错也照样能改成新密码**；
- 直到后端上线，这一栏才真正开始拦截。

也就是说，那段时间里这是一个**看起来已经生效、实际没有生效的安全控件**。
前端无法自行消除这个窗口（见第四节，三条替代路径都被否掉了），
所以优先级由后端判断 —— 而虚假安全感比不显示这一栏更糟，这正是催办的理由。
