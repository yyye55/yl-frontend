## 三、前端已修：三个页面的「组别」下拉传了不存在的值

### 3.1 问题

三个页面的「组别」下拉，选项写的是**拼接串**「管乐团-小学组」「铜管乐团-中学组」这类值。

但「管乐团 / 铜管乐团」和「小学组 / 中学组 / 大学组」在后端是**两个独立列**：

| 列 | 含义 | 取值 |
|---|---|---|
| `Report.establishment`（`models.py:220`） | 乐团类别 | `"管乐团"` / `"铜管乐团"` |
| `Report.group`（`models.py:219`） | 参演组别 | `"小学组"` / `"中学组"` / `"大学组"` |

第十二届的 5 个正式组合（管乐团×{小学,中学,大学} + 铜管乐团×{小学,中学}）
是**这两个维度的乘积**，不是 `group` 列的取值。

而这三个页面对 `group` 走的都是**精确过滤**，`group` 列里又没有「管乐团-小学组」这个字符串 ——
**所以选任何一项都是整页空表。** 这就是「组别下拉一选就空白」的原因。

### 3.2 三条链路（这就是「取错值必然空表」的证据）

| 页面 | 前端调用 | 后端接口 | 后端函数 | 对 group 的处理 |
|---|---|---|---|---|
| `/admin/report` | `adminApi.report.getList` | `GET /api/admin/report/list` | `report_queryset`（`views.py:95`） | `:127` `qs.filter(group=...)` 精确 |
| 组委会展演页 | `committeeApi.online.getList` | `GET /api/committee/online/list` | `views.py:937` → `role_error(2) or live_page` | `:251` `qs.filter(group=...)` 精确 |
| 展演列表页 | `liveApi.getLiveReportList` | `GET /api/live/list` | `live_page`（`views.py:241`） | `:251` `qs.filter(group=...)` 精确 |

### 3.3 改法（已完成，纯前端）

三个下拉统一改成真值，**与后端取值逐字相同**：

```
全部（null，不传参数） / 小学组 / 中学组 / 大学组
```

涉及文件（前端仓库，**不需要你们动**）：

- `src/views/admin/report.vue`
- `src/views/committee/online.vue`
- `src/views/online/list.vue`

三处的注释里都写明了取值依据与对应的后端文件行号。
`npm run build` 已通过。

> 「管乐团 / 铜管乐团」这一维度本次**还筛不了** —— 原因见第四节。

## 四、后续改法（本次请评估，不急）

### 4.1 请求：给两个列表接口增加 `establishment` 过滤参数

> ⚠️ 这一条要改后端，所以**先问你们，不默认做**。你们评估后说行不行都可以。

**现状**：组别（小学组/中学组/大学组）现在能筛了，但**「只看铜管乐团」筛不出来**。

**我们本想要的界面**：两个下拉 —— 「乐团类别：全部 / 管乐团 / 铜管乐团」+「参演组别：全部 / 小学组 / 中学组 / 大学组」，
这样 5 个正式组合就能自由组合出来，也与红头文件的表述一一对应。

**卡在哪**：后端没有第二个参数。`report_queryset`（`views.py:95-131`）和 `live_page`（`:241`）
都只读 `keyword / status / group`，没有 `establishment`。

**建议改法（纯增量，不带参数时行为逐字不变）**：

`apps/api/views.py` —— `report_queryset` 里，在 `group` 那段（`:126-127`）旁边加一段：

```python
    if request.GET.get("establishment") not in (None, ""):
        qs = qs.filter(establishment=request.GET.get("establishment"))
```

`live_page`（`:241`）同样加一段，供两个展演页使用。

前端会按「参数为空就不传」的方式接，因此**不传 `establishment` 的请求与改动前完全等价**，
不会影响任何已有调用方。

**为什么不建议反过来「把两个维度拼成一列存」**：
`group` 这个列现在被四处依赖 ——
`registration_form.py:260`（校验白名单 `("小学组","中学组","大学组")`）、
`views.py:512`（统计三档）、
`export_services.py:97`（导出映射 `{"小学组":1,"中学组":2,"大学组":3}`）、
`migrations/0009` 的字段注释。
动这一列要连带改四处 + 洗历史数据；而加一个过滤参数是零风险的。

**如果你们评估后不想加**：也回我们一声就行。我们会把这两个下拉维持现状
（组别能筛、类别不能筛），并把这个限制写进前端注释，**不再提这个需求**。

### 4.2 想跟你们确认一个行为变化（不是缺陷，是问「是否符合预期」）

`fa40f76` 把 `/export/report`（报名信息表）、`/export/person`、`/export/data`
三条导出接口从 `status__gte=0` 收紧成 `status=1`（只导**已通过**）。

这三条接口，前端用在**市州端 / 学校端 / 中小学端首页的「导出报名信息表」按钮**上。
而那个按钮的确认文案是：

> 「此操作需在所在单位账号**所有数据都已报送完毕**后操作，确认操作？」

**想确认的是：「已报送」是否等于「已审核通过」？**

- **如果相等** —— 没问题，我们照用，本节结束。
- **如果不相等**（报送 = 已提交，其中含待审核 `status=0`）—— 用户会遇到
  「我明明全部报送完了，导出的表却是空的 / 少了几条」，因为组委会还没审到那几条。

请你们判断这是否是预期行为。**若是预期**，我们这边可以顺手把按钮文案从
「所有数据都已报送完毕」改成「所有数据**都已审核通过**」，让用户不至于困惑 ——
这属于纯前端文案，不动后端，等你们答复后再定。

**另注**：`/admin/export/data1|2`（`Report.objects.all()`）与 `/committee/export/data`
（只按可选 `group` 过滤）**没有**收紧 status，与本条无关。
