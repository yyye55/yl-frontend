## 一、已修：同一所学校报完中学组后，报不了小学组

### 1.1 用户报上来的原始症状

市级账号（即有小学也有中学的那类学校）报完中学组后，再报小学组被拒：

```
POST http://47.108.29.34/api/city/report/drafts/5/submit
→ 409 { code: "REPORT_QUOTA_EXCEEDED",
        msg: "每所学校限报一支队伍，您已有报名记录" }
```

而页面承诺的不是这个口径。用户原话：

> 一个账号肯定对应一个学校。意林杯器乐展示活动有部分学校有小学也有中学，可以报送 2 支队伍。
> 系统上注意一下哈。但是现在我报了中学之后就无法再报小学了。

### 1.2 根因

`apps/core/report_drafts.py` 的 `assert_report_quota` **只按账号计数、完全不看组别**：

```python
limit = REPORT_QUOTA_BY_SCOPE.get(scope, DEFAULT_REPORT_QUOTA)   # 市级 = 1
current = Report.objects.filter(user_id=user.id).count()          # ← 不看 group
if current >= limit:
    raise ReportQuotaExceeded("每所学校限报一支队伍，您已有报名记录")
```

一个账号对应一所学校，所以「中学组」占掉了那唯一的名额，「小学组」永远轮不到。
它把**小学组和中学组当成了同一个池子**。

### 1.3 口径依据（不是我推测的，是仓库里已有的书面口径）

`yl-frontend/src/components/common/HaveToRead.vue:61-67` 的【2026-09-23 口径变更】：

```
红头文件原文是「每所学校限报一支队伍，且只能参加一个组别。」组委会后来放宽：
有同时设小学和中学的学校，本就应当能各报一支。现口径为
「每所学校每个组别限报一支队伍，小学组、中学组可各报一支（最多两支），大学组限报一支」。
本节与后端额度校验（apps/core/report_drafts.py 的 assert_report_quota）必须同步，
只改此处会让页面承诺的额度与系统实际放行的额度对不上。
```

**所以是后端漏跟了口径变更，不是口径要改回去。** 那段注释自己都写了「必须同步」。

### 1.4 改动（后端 `1d50aec`：2 个源文件 + 1 个测试文件，+63/−7）

| 文件 | 改动 |
|---|---|
| `apps/core/report_drafts.py` | `assert_report_quota(user, scope, group=None)` 新增 `group` 参数，计数时 `filter(group=group)`。**取不到 group 时退回账号级计数**（宁严不松，不会凭空多放行一支）。额度值 `REPORT_QUOTA_BY_SCOPE` 未动。 |
| `apps/api/views.py:128` | `create_report` 传入 `data.get("group")` |
| `apps/core/report_drafts.py:272` | `create_report_from_submission` 传入 `submission.report.get("group")` |

全仓只有这两个调用点（`grep -rn assert_report_quota apps/` 可验），都已改。

**顺带修正了报错文案。** 原来那句「每所学校限报一支队伍，您已有报名记录」没说清是**哪个组**
满了 —— 这正是用户被误导的原因。现在形如：

```
中学组每所学校限报一支队伍，您已有报名记录
```

`reportDraft.js:205` 也注明 `msg` 是用户唯一能知道发生了什么的渠道，故前端原样透传。

## 二、已修：市级渠道不得报送「大学组」（新增渠道组别白名单）

### 2.1 现象

一个市级账号报了小学组 + 中学组之后，**再提交一个 `group="大学组"` 的报名会被放行**，变成 3 支。

### 2.2 关键：这不是「配额修复」引入的漏洞

修复前，市级账号在**一支都没有**的时候本来就能报大学组 —— 因为配额只挡第二支，
而计数字段根本没有 group 这个概念。这个洞一直存在。第一轮把上限从「1 个大学组」改成
「每组一支」时只是**换了洞的形状**，没堵也没捅大。本次是把它堵上。

### 2.3 口径（组委会 2026-09-23 确认，不是我们推测的）

> city 渠道不能出现大学组，铜管乐团同规则。最多两支；可以只报一支；
> 如果要报两个队伍，必须是一个小学一个中学。

`OrchestraForm.vue:478-482` 早就把这条写下来了：

```
【结论】city 渠道不该出现「大学组」，与乐团类型（管乐/铜管）无关：
  管乐团 × city   → 小学组、中学组（大学组归高校渠道）
  铜管乐团 × city → 小学组、中学组
  管乐团 × school → 大学组
```

### 2.4 改动：`apps/core/report_drafts.py`

```python
REPORT_ALLOWED_GROUPS = {1: ("小学组", "中学组")}          # 只配了 scope 1
REPORT_SCOPE_LABELS = {0: "高校端", 1: "市级渠道", 4: "省级端"}   # 只用于拼文案

def assert_group_allowed(scope, group): ...              # 不在表内 → 一律放行
```

并**在 `assert_report_quota` 的第一行调用它**，而不是在两个调用点各加一遍。

**为什么挂在 `assert_report_quota` 里（这里有个命名上的坑，先说清楚）**：
全仓只有两个调用点（`views.py:128`、`report_drafts.py:272`），都是新建报名的必经之路。
挂进被调函数里，两个入口自动覆盖，将来多一个调用点也不会漏。
**代价是函数名只说了 quota，组别校验是搭车的** —— 已在该函数 docstring 首段写明，
看代码时别被名字误导。

### 2.5 ⚠️ 为什么抛 400 而不是 409（**这条最容易被顺手改回去，请务必保留**）

新增的拒绝**故意复用已有的 `InvalidSubmission`（HTTP 400，码 `SUBMISSION_VALIDATION_FAILED`）**，
而不是跟配额一样抛 `ReportQuotaExceeded`（HTTP 409）。原因完全在前端，是行为差异，不是风格偏好：

`yl-frontend/src/api/reportDraft.js` 的 `normalizeDraftError` **只对已登记的错误码单独分支**，
未登记的码退到「按 HTTP 状态兜底」：

| 后端返回 | 前端归一成 | 用户实际看到 |
|---|---|---|
| 未登记码 + **409** | `CONFLICT` | **硬编码的**「该草稿已在其他页面或设备更新」，外加一个**「重新加载服务器草稿」按钮** —— 这个按钮解决不了「组别选错了」，而且提示本身是假的 |
| 未登记码 + **400** | `INVALID` | 走 `OrchestraForm.vue` 的 `notifyDraftError` 兜底分支，`ElMessage.error(e.msg)` —— **原样显示后端文案** |

所以 400 让用户看到的是「市级渠道只能报送小学组或中学组，不能报送大学组」，
409 让他看到一句假话加一个没用的按钮。

**选 `SUBMISSION_VALIDATION_FAILED` 还有第二个好处：这个码前端已经登记了**
（`reportDraft.js:180-184` → `INVALID`），所以**本次改动前端一行都不用改**。
`reportDraft.js:203` 那句「前端不自己判额度，一律以后端为准」也依然成立 ——
组别合法性同样以后端为准。

### 2.6 为什么表里只有 scope 1

| scope | 是否配表 | 理由 |
|---|---|---|
| 0 高校端 | ❌ 不配 | 组委会明确要求本次**不加**这条校验 |
| 1 市级 | ✅ `("小学组", "中学组")` | 本次要堵的就是它 |
| 4 省级 | ❌ 不配 | 本届红头文件没有省级端（见第三节），不为历史代码写新规则 |

**未配表的 scope 一律放行。** 这个默认方向是刻意选的：将来新增渠道忘了配表，
后果是「不校验」，而不是「所有用户被拦死」。

**顺带被这条规则自动满足的三件事**（不需要额外代码，见 2.7 验证）：
最多两支、可以只报一支、报两支必然一小学一中学 —— 渠道只放两个组别，
配额又按组别各 1 支，两者相乘即上限 2。两支的**乐团类型互相独立**
（小学管乐团 + 中学铜管乐团是允许的），后端 `establishment` 与 `group` 之间零耦合，本来就自由。

## 三、刻意不动：省级端（scope 4）以及它带来的额度语义变化

> **本节结论已定：先放着，不处理。** 以下是背景，供将来清理时参考。

### 3.0 省级端是上一届的遗留，本届根本不存在

用户原话：

> 因为这个省级端是当时西部音乐周留下来的 dist 包里面的，但是这届的这个意林杯
> 根本就没有省级端。

也就是说 `TYPE_PROVINCE=4`、9 条 `/api/province/*` 路由、`REPORT_QUOTA_BY_SCOPE[4]`
这一整套都是上次活动搬过来的**死代码**，本届红头文件里没有省级端这个东西。
所以第三节下面讲的语义变化**没有实际受害者**，不值得为它加特例分支。
（彻底删除是另一件事，需要先在生产库确认有没有 `type=4` 的存量账号，见 3.4。）

### 3.1 现象

`REPORT_QUOTA_BY_SCOPE = {0: 1, 1: 1, 4: 8}` 未改，但计数口径变成按组别之后：

| | 修复前 | 修复后 |
|---|---|---|
| `scope 4`（省级） | 本账号名下**总共** 8 支 | **每个组别** 8 支 |

省级路由仍然注册着（`apps/api/views.py:973` `register_scope_routes("/province", 4, True)`，
即 `POST /province/report/create` → `create_report(request, province=True)` → `scope=4`），
所以这条路径是活的。注意省级**没有**走草稿链路（`register_draft_routes` 只注册了
`/city` 和 `/school`），所以它只经过 `create_report`，也就是本次改的另一个调用点。

### 3.2 实际影响面：接近零，但语义确实变了

前端 `src/router/index.js:6` 写明：

```
5 个 layout：admin / committee / city / school / online（省级端已下线）
```

省级端页面已下线，没有前端入口；要触发得有一个 `type=4` 的账号直接打接口。
所以**实践中不会有人碰到**。

### 3.3 结论：保持现状

- 新增的 `REPORT_ALLOWED_GROUPS` **刻意没有 scope 4** —— 不为历史代码写新规则，
  未配表即放行，省级端行为与加白名单之前完全一致；
- `REPORT_QUOTA_BY_SCOPE = {4: 8}` 也没动。它现在的语义是「**每个组别** 8 支」，
  与改动前的「**总共** 8 支」不同 —— 但省级端已下线、无前端入口，实践中碰不到。
  已在本文件写明，免得下一个人看到 `{4: 8}` 又猜一遍。

### 3.4 将来真要删的话（我们做不了，需要你们配合）

**前置条件**：在生产库跑一次

```sql
SELECT type, count(*) FROM users GROUP BY type;
```

只有确认 `type=4` 的账号数是 0（或都是可弃的历史账号），删除才安全 ——
我们**没有生产库的读权限**，这一步做不了。

清点过的牵连点（供届时参考）：

| 位置 | 内容 |
|---|---|
| `apps/core/models.py:76-80` | `User.TYPE_PROVINCE = 4` |
| `apps/api/views.py:969-973` | `register_scope_routes("/province", 4, True)`（注意：省级**没有**草稿路由） |
| `apps/api/views.py` | `create_report(province=True)` 与其 `if province:` 分支 |
| `apps/api/views.py:678-698` | `scoped_total` 的省级兜底分支 —— **本来就是坏的**（按 `group=str(group)` 查 0/1/2/3） |
| `apps/api/views.py:511` | 导出文件里的用户可见文案「密码找回请联系省级行政部门」 |

| 前端 | `committee/user.vue`、`login/index.vue:144`、`middle/index.vue:12`，以及若干死变量与注释 |

**注意 `views.py:469-495` 那两处**：删 `TYPE_PROVINCE` 时如果只删常量，这两处
`type__in=(0, 4)` 依然合法（`4` 只是个整数），会静默地什么都不匹配、也不报错。
