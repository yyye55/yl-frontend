## 零、怎么读这份文档

### 触发原因

甲方在管理员端的「人员管理」页（`/admin/person`）提出两条：

1. 搜索框**按学校名搜不到人**；
2. 该列表建议加一个按「填报单位」筛选的功能。

前端顺带把三处列头文案由「学校名称」改成了「填报单位」（见第六节）。

### 结论一句话

**两条都卡在后端**：`/api/admin/person/list` 的 `keyword` 只匹配 `name` / `card`，**不含 `school`**；
且该接口**没有 `school` 参数**，所以前端也无法做服务端筛选。

`Person.school` 字段是**存在的**（`apps/core/models.py:258`）——**不是字段缺失，是过滤条件没写**。

## 一、现状取证

### 1.1 后端原文

`apps/api/views.py:560-566`，逐字：

```python
@api.get("/admin/person/list", auth=auth)
def admin_person_list(request):
    err = role_error(request, 3)
    if err: return err
    qs = Person.objects.all().order_by("id"); k = request.GET.get("keyword")
    if k: qs = qs.filter(Q(name__icontains=k) | Q(card__icontains=k))
    return response(list_page(qs, request, model_dict))
```

第 565 行的 `Q(...)` 只有两个分支。**传进去的单位名一个都匹配不上。**

### 1.2 字段确实存在

`apps/core/models.py:252-258`：

```python
class Person(models.Model):
    id = models.BigAutoField(primary_key=True)
    name = models.CharField(max_length=255, default=" ")
    user_id = models.IntegerField()
    card = models.CharField(max_length=255, unique=True, default=" ")
    age = models.IntegerField(null=True, blank=True)
    school = models.CharField(max_length=255, null=True, blank=True)
```

### 1.3 前端没有做小动作

前端 [src/views/admin/person.vue](../../src/views/admin/person.vue) 把 `keyword` **原样**发出：

```js
adminApi.person.list({ page: page.value, limit: limit.value, keyword: keyword.value })
// → GET /api/admin/person/list?page=&limit=&keyword=
```

前端没有截断、没有改写、没有只发部分字段。**改不动就是改不动。**

### 1.4 怎么自己复现

拿一个**确实存在于 `Person.school` 里**的单位名（可从库里任选一条 `Person` 的 `school` 值），
用它当 `keyword` 调接口：

```bash
curl -s 'http://47.108.29.34/api/admin/person/list?page=1&limit=5&keyword=<某个确实存在的单位名>' \
  -H 'Authorization: Bearer <管理员 token>'
```

**实际结果**：`{"code":0,"count":0,"data":[]}`
**预期结果**：`count` 至少是该单位的人员数。

反过来，把 `keyword` 换成**同一个人的姓名**，就能查到 —— 这正说明 `keyword` 本身是通的，
只是匹配字段少了 `school`。

## 二、需求 A：让搜索覆盖「填报单位」

**把 `Q(school__icontains=k)` 加进第 565 行那个 `Q(...)` 即可。** 一行改动：

```python
if k: qs = qs.filter(Q(name__icontains=k) | Q(card__icontains=k) | Q(school__icontains=k))
```

**兼容性**：只是把 `Q` 的匹配面从 2 个字段扩到 3 个。
- 不会让任何原本能查到的结果消失（`Q` 是「或」，只会变多）；
- 不改变返回结构、不改分页语义；
- 唯一可预期的副作用：搜一个既是人名又是单位名片段的词时，结果会变多 —— 这正是需求要的。

---

## 三、需求 B：新增 `school` 筛选参数

搜索框和筛选框是**两件事**：搜索是一个模糊词打三个字段，筛选是**只在单位上做限定**。
所以还需要一个独立参数。

### 3.1 契约

```
GET /api/admin/person/list?page=1&limit=10&keyword=&school=成都七中
```

| 参数 | 语义 | 缺省行为 |
|---|---|---|
| `school` | 对 `Person.school` 做 `icontains` 模糊过滤 | **不传或空串 → 行为与现在完全一致** |

- `keyword` 与 `school` **同时传 → 取交集**（先按 `keyword` 过三个字段，再按 `school` 限定单位）；
- `school` 用 `icontains`（模糊），**不是精确匹配** —— 理由见 3.3；
- 响应结构、分页信封（`{code,msg,data,count}`）**一律不变**，无需前端改动解析。

### 3.2 精确 patch

相对 `apps/api/views.py:564-565`：

```python
    qs = Person.objects.all().order_by("id"); k = request.GET.get("keyword")
    if k: qs = qs.filter(Q(name__icontains=k) | Q(card__icontains=k) | Q(school__icontains=k))
    s = request.GET.get("school")
    if s: qs = qs.filter(school__icontains=s)
    return response(list_page(qs, request, model_dict))
```

第 4 行的 `if s:` 顺带兜住了 `school=`（空串是假值）的情况，不用额外判空。

### 3.3 为什么用 `icontains` 而不是精确匹配

`Person.school` 是**各校在报名表单的人员表里手填的自由文本**，不是外键、没有字典表。
同一所学校完全可能出现「成都七中」「成都市第七中学」「成都七中 」这类写法差异。
精确匹配会让筛选框稍差一个字就查不到人，反而像坏了。**模糊匹配更符合实际数据质量。**

> 如果后端希望改成精确匹配，请先告知：前端会改成下拉选择，那就需要先做第四节的单位清单接口。

## 四、不需要改的：参展扫描件列表

甲方同时提到组委会端 / 管理员端的「参展扫描件列表」。**这一页后端不用动。**

该页列头文案同样由「学校名称」改成了「填报单位」，但**它的搜索本来就是好的**：

`apps/api/views.py:325-330`：

```python
@api.get("/scan/list", auth=auth)
def scan_list(request):
    types = [0, 1, 4]
    qs = User.objects.filter(type__in=types).order_by("id")
    if request.GET.get("keyword"):
        qs = qs.filter(nickname__icontains=request.GET["keyword"])
```

而该页显示的那一列正是 `nickname`（`User.nickname`，即账号所属的填报单位）。
**key 与 value 是同一个字段，所以搜索命中率是 100%。** 前端只改了个列头字符串。

特此写明，免得后端为这一页白跑一趟。

## 七、后端改完之后我们怎么验

1. 用某个确实存在的单位名当 `keyword` 调 `/api/admin/person/list` → `count > 0`（需求 A）；
2. 传 `school=<单位名片段>` → 只返回该单位的人员，`count` 与库里对得上（需求 B）；
3. **同时**传 `keyword=<姓名>` 和 `school=<单位名>` → 取交集；
4. 两个参数都不传 → 结果与改动前逐字节一致（回归）；
5. 前端在 `/admin/person` 上做一次人工核对，确认列表值照常显示、搜索行为未回归。
