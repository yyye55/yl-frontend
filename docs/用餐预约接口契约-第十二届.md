# 用餐预约 —— 接口契约（第十二届）

> 交接对象：后端。前端按本契约实现 UI，后端按本契约改导出与校验。
> 这份文档是「用餐预约」的**唯一事实来源**；《后端协助问题清单》P1-4 只描述问题，
> 不再重复契约内容。两边如有出入，以本文件为准。

## 一、唯一事实来源：红头文件附件2 的表格本身

`“意林杯”四川省第十二届管乐展示活动 - 系统需求.docx` → 附件2《报名信息表》，
「用餐预约」栏是一个左侧标签列 + 右侧四个格，逐字如下（上表头、下填写行）：

| 用餐预约 | 11月21日午餐 | 11月21日晚餐 | 11月22日午餐 | 11月22日晚餐 |
| --- | --- | --- | --- | --- |
|  |  |  |  |  |

同页备注 1 原文：

> 备注：1. 如果需在成都理工大学食堂购票用餐，请备注时间并在对应位置写上**就餐人数**。

由这两处得到本功能的全部硬性要求，只有两条：

1. **4 格**，且日期固定为 `11月21日` `11月22日` 的午/晚（**没有 11月20日**）。
2. 格子里写的是**就餐人数**（一个整数），不是「选没选」的勾。

「时间」不是单独一个输入项 —— 它由**填在哪一列**表达（21日午餐 / 21日晚餐 /
22日午餐 / 22日晚餐）。所以 UI 与数据模型都只需要「4 个整数」。

> 关于 11月20日：文件正文只写了「报到时间：2026年11月20日8:00—12:00」与
> 「展示时间：2026年11月20日至22日」，**并未说明**为何用餐栏不含 20 日。
> 表格样式以附件2 为准，不在本文档里替组委会解释原因。
> 若组委会确实希望增加 20 日的两餐，应当先改附件2 本身 ——
> 而不是让系统导出的表比红头文件多出两格。

## 二、现状与文件的差异

三处，全部需要后端改动（前端另需新增 UI，见第五节）。

| # | 位置 | 现状 | 应改为 |
| --- | --- | --- | --- |
| 1 | `apps/api/registration_form.py:17` `MEALS` | 6 格，含 `11月20日午餐/晚餐` | 4 格 |
| 2 | `registration_form.py:56` `_meal_cells()` | 每格写死 `"√"` | 每格写**人数** |
| 3 | 数据语义 | `dinner_reservation` = 「选中了哪些格」的字符串集合 | 每格一个人数 |

第 2 条的具体机理（`registration_form.py:65-79`）：

```python
for item in _json_list(report.dinner_reservation):
    text = str(item).strip()
    if text.isdigit() and 0 <= int(text) < len(MEALS):
        cells[int(text)] = "√"          # 下标写法：直接写死 √
    else:
        for index, label in enumerate(MEALS):
            if text == label or all(part in text for part in MEAL_HINTS[index]):
                cells[index] = "√"      # 文案/简写写法：同样写死 √
```

两处都会把人数丢掉（以下均为**实测**结果，非推理）：
- 传下标 `"2"` → `cells[2] = "√"`，**「2」是下标不是人数**，语义完全错位；
- 传 `"11月21日午餐20人"` → **`cells[0] = "√"`**，即写进了 **11月20日午餐**。
  原因是 `"20人"` 的 **20** 命中了 `MEAL_HINTS[0] = ("20","午")`，
  而循环**命中即 break**，正确的 21 日那格根本没走到。
  **人数被丢 + 落到错格**，两格在导出的表格上却都「看起来正常」。

现在唯一能保住人数的办法是故意传一个匹配不上的字符串，让它落进 `leftovers`，
再由 `form_context():117-118` 追加到备注栏：

```python
cells, leftovers = _meal_cells(report)
if leftovers:
    remark_parts.append("用餐预约：" + "、".join(leftovers))
```

**靠兜底路径承载正常语义是脆的**：任何一次把匹配规则改宽，这些字符串就会被
吞成 `√`，人数无声消失。契约改完后这条兜底应当**删除**，见第四节。

## 三、契约

### 3.1 线上格式

字段沿用 `Report.dinner_reservation`（`LegacyJSONField`，`apps/core/models.py:188`）。
**格式改为「对象数组」**：

```json
[
  { "meal": "11月21日午餐", "count": 20 },
  { "meal": "11月22日晚餐", "count": 8 }
]
```

规则：

- 元素是对象，只有两个键：`meal`（字符串）、`count`（整数）。
- **`meal` 必须逐字等于下面四个之一**（不许简写、不许下标、不许加空格）：

  ```
  11月21日午餐   11月21日晚餐   11月22日午餐   11月22日晚餐
  ```

- `count` 为整数，范围 `1 ≤ count ≤ 500`。（上限是防手滑的兜底值，
  红头文件对人数无规定；乐团规模上限见文件「管乐团正式成员…不超过65人」。）
- **不预约的餐次不要出现**，不要发 `count: 0` 的元素。
- 空数组 `[]` = 一餐都不订，是合法值，也是默认值。
- 同一个 `meal` 重复出现 → 400，不做「后者覆盖前者」。

### 3.2 为什么是对象数组，而不是别的

**先说清楚一件事：现在这三种格式没有一种是对的。**

下表的「现状」一列是把每种格式直接喂给**当前**的 `_meal_cells()` 跑出来的实际结果
（`registration_form.py:19` 的 6 格口径），不是推理：

| 格式 | 现状（实测） | 契约改完后 |
| --- | --- | --- |
| `[{"meal":"11月21日午餐","count":20}]` | `cells[0]="√"` —— 落进 **11月20日午餐** | ✅ 正确 |
| `[{"meal":"11月22日晚餐","count":8}]` | `cells[5]="√"` —— 碰巧**是对的** | ✅ 正确 |
| 下标数组 `[0,20,0,8]` | `cells[0]="√"` —— `0` 被当下标，`20`/`8` 超出范围被忽略 | ❌ 仍然错位 |
| 顶层对象 `{"11月21日午餐":20}` | `cells[0]="√"` —— 落进 **11月20日午餐** | ❌ 无（形状不对） |

看第二行：同一个「对象数组」格式，换个餐次就**时对时错**。
原因是 `_meal_cells` 把元素 `str()` 化之后做**子串包含**匹配 ——
`"{'meal': '11月21日午餐', 'count': 20}"` 里恰好同时有 `"20"` 和 `"午"`，
于是命中 `MEAL_HINTS[0]`。**它根本不看格式，只是在字符串里找片段。**

所以选格式的标准不是「现在跑不跑得通」（都跑不通），而是：

> **改成严格校验之后，后端有没有能力判断这条数据对不对？**

- 对象数组里的 `meal` 是**可枚举校验的字符串** —— 四个合法值之一，认不出来就是 400。
  `count` 是**可校验的整数**。
- 下标数组 `[0,20,0,8]` **根本不含餐次信息**。后端拿到它无法判断「20 是不是该记在 21 日午餐」——
  它只能假设前端和它对格数与顺序的理解完全一致。一旦不一致（比如后端 6 格、前端 4 格），
  数据就**静默错位**，而且导出表上看起来完全正常。这是本合同要消灭的那类错误。

**顶层对象**另外还有一个独立的坏处：`/admin/export/data1`（`export_services.py:202`）是
`"、".join(str(x) for x in dinner)`，dict 会被原样打印成 Python 的 repr 进 Excel 单元格。
对象数组虽然也要改那一行（见 4.2），但改成「21日午餐 20人」是自然的；
dict 的形状本身就是给机器看的，不适合直接落表。

> 【更正】本文件初稿在这里写过「顶层对象会静默丢失、整条进备注栏」，
> **不对**。实测它落进了 `cells[0]`（21日午餐）或 `cells[5]`（22日晚餐），
> 是被**错格渲染**，不是被丢弃。已按实测改写。

另外，**列表形状不要动**。`report_drafts.py:154-157` 目前对
`dinner_reservation` 只校验「是 list 或 dict」，不校验元素：

```python
elif field == "dinner_reservation":
    if value is not None and not isinstance(value, (list, dict)):
        raise DraftError("dinner_reservation 必须是数组或对象")
    result[field] = value
```

前端也是按数组透传的（`draftPayload.js:214` 与 `:280` 两处都是
`Array.isArray(...)` 守卫）。保持数组形状，**前端这两个文件一行都不用改**；
改成顶层对象则会被这两处守卫静默丢弃。

> 后端若愿意在草稿层顺带做元素校验（校验 `meal`/`count`），是加分项，但不作要求 ——
> 提交时的校验（`parse_submission_payload`）必须做，见 4.3。

## 四、后端改动清单

### 4.1 导出（`apps/api/registration_form.py`）

1. `MEALS` → 4 项；`MEAL_HINTS` 同步收敛为 4 项。
   ```python
   MEALS = ("11月21日午餐", "11月21日晚餐", "11月22日午餐", "11月22日晚餐")
   ```
   `MEAL_LABELS`（`:20` 的 `label[:6]<br/>label[6:]` 换行）对 4 项依然成立，
   因为四个标签都是「6 字日期 + 2 字餐次」，不用改。
2. `_meal_cells()` 重写为「读人数、写人数」：
   - 每格输出 `str(count)`，未预约的格输出 `""`（空字符串，`cell()` 会渲染成空格）；
   - **删除 `leftovers` 返回值和 `_meal_cells` 里的 `MEAL_HINTS` 宽松匹配**；
   - 遇到不认识的格式怎么办见 4.4。
3. `form_context():117-118` 的 `remark_parts.append("用餐预约：" + ...)` 一并删除。
   契约改完后没有任何合法输入会落进 `leftovers`，这条兜底只会把错误藏起来。

### 4.2 ⚠️ 别漏了 Excel 导出（`apps/api/export_services.py:202`）

这一处最容易漏。`/admin/export/data1` 现在是：

```python
dinner = _json_list(item.dinner_reservation)
...
"、".join(str(x) for x in dinner),
```

格式一改，这一格会直接打印出 Python 字典的 repr：

```
{'meal': '11月21日午餐', 'count': 20}
```

需要同步改成人类可读的形式，建议：

```
11月21日午餐 20人、11月22日晚餐 8人
```

`Draft` 与正式库共用这一列，两个导出（附件2 PDF / data1 Excel）读的是同一份数据，
改格式必须两处一起改。

### 4.3 提交校验（`apps/core/report_drafts.py`）

在 `parse_submission_payload`（或 `normalize_draft_payload`）里对
`dinner_reservation` 加元素级校验，非法值一律 400 并给出中文 `msg`：

- 元素不是对象 → `用餐预约格式不正确`
- `meal` 不在四个标签内 → `用餐预约餐次不正确：<值>`
- `count` 不是整数 / `<1` / `>500` → `用餐预约人数不正确：<值>`
- 同一 `meal` 重复 → `用餐预约餐次重复：<值>`

**必须报错而不是静默忽略** —— 这正是现在这套实现的问题所在。

### 4.4 存量数据

先查一下有没有：

```sql
SELECT id, school_name, dinner_reservation
FROM report
WHERE dinner_reservation IS NOT NULL
  AND dinner_reservation NOT IN ('', '[]', 'null');
```

`report_draft` 表同理（改过没提交的草稿里可能也有）。

- 若结果为空 —— 最好，直接切契约。
- 若有值 —— 需要给出迁移口径。**注意这些值大概率是测试数据**：
  前端从来没有绑定过这个字段的控件（见第五节），真实用户没有途径填出内容。

不论哪种情况，`_meal_cells` 都应**容忍旧格式**（把 `"√"` / `"21午"` 这类旧值
当作「有预约、人数未知」处理，而不是让整个导出抛异常）。
旧格式的具体降级方式请后端定，前端不依赖它。

### 4.5 ⚠️ 现有两个测试**断言的正是要删掉的行为**

`tests/test_export_form.py` 里这两例会变红，**这是预期的**，不要为了让它们变绿而
把旧行为留下：

```python
def test_meal_slots_accept_index_label_and_abbreviation(self):     # :77
    self.report.dinner_reservation = [0, "11月21日晚餐", "22午"]
    ...
    self.assertEqual(cells, ["√", "", "", "√", "√", ""])          # ← 6 格 + √

def test_unmatched_meal_entry_moves_to_remark(self):              # :85
    self.report.dinner_reservation = ["10月1日午宴"]
    ...
    self.assertIn("用餐预约：10月1日午宴", ctx["remark"])            # ← leftovers 兜底
```

- 第一个把「下标 / 简写 / 写 √」三件事**一起断言成了正确行为** ——
  它正是 3.2 表里那个静默错位陷阱的守护者。要改成新格式的用例。
- 第二个断言的是 4.1 第 3 条要求删除的兜底路径。要删掉，
  或反向改成「非法 `meal` 应当 400」。

「用餐预约」此前**只有这两个用例**，且都在断言错的行为 —— 这也是它坏掉这么久
没被发现的原因之一（与 P2-3 是同一类问题）。

## 五、前端改动清单（本轮不做，等契约确认后一次做对）

现状：`OrchestraForm.vue:588` 的表单初值里有 `dinner_reservation: []`，
但**模板里没有任何控件绑定它**（`OrchestraForm.vue:395` 已注明）。
全仓 grep `dinner_reservation` 只有 8 处，全部是初值、类型注释、`draftPayload` 透传 ——
**没有一处是 UI**。也就是说一所学校想订 21 日午餐 20 份，在系统里没有任何地方可以填。

契约确认后，前端需要做的：

1. 在报名表单里新增「用餐预约」一组控件（4 个数字输入，标签即四个餐次）；
2. 提交/暂存时按 3.1 组装成对象数组；
3. 回填时按 `meal` 精确匹配到对应输入框。

**`draftPayload.js` 不需要改**（见 3.2）。

前端本轮**故意不做**，理由：

1. 现在做只能发「选没选」，红头文件要的人数照样丢 —— 会做出一个**看起来能用、
   实际丢数据**的控件，比没有控件更坏（用户会以为已经填过了）。
2. 按 4 格发下标会静默错位到 20 日（见 3.2 表格）。
3. 目前没有学校能用这个字段，**存量数据几乎为零**，改契约的代价此刻最低。
