## 一、为什么"两边不一样"是当前最大的隐患

核对结果（依据：本仓前端源码 + `d:/yl-all/yilinbei` 后端源码）：

| 校验点 | 前端 | 后端 | 现状 |
|---|---|---|---|
| 必填 | `el-form` rules，逐条中文提示 | 只有 DB `NOT NULL` 兜底（缺字段 → 500） | 前端独有 |
| 长度 1–100 / 1–20 / 300 | 有 | `max_length=255`（`desc` 1000） | 前端更严 |
| 自选曲目首《》末《》 | `nameValidator` | 无 | 前端独有 |
| 指定曲目候选（9 条） | 下拉白名单 | `CharField(255)` 任意字符串 | 前端独有 |
| 类型 / 组别取值 | 下拉 | `CharField(255)`，无 `choices` | 前端独有 |
| 时长上限 12/15/18/10 | `personRules.js` | `time_length` 整数，无上限 | 前端独有 |
| 人员编制 35–65 / 预备 / 打击乐 | `personRules.js` | 完全没有 | 前端独有 |
| 指导教师 ≤ 3 人 | 提交时判 | 无 | 前端独有 |
| 人员行 9 个必填列 | `checkLine` 逐行 | 只判姓名 + 身份证 | 前端更严 |
| 性别 男/女 | 下拉 + 导入校验 | `CharField` 任意 | 前端独有 |
| 身份 / 角色取值 | 下拉 0/1/2 | `IntegerField`，无范围 | 前端独有 |
| 乐器 17 项 | 下拉 | `CharField` 任意 | 前端独有 |
| 身份证号格式 | ❌ 无 | ❌ 无 | **两边都没有** |
| 手机号格式 | ❌ 无 | ❌ 无 | **两边都没有** |
| 年龄范围 / 整数性 | ❌ 只判非空 | `IntegerField`（非整数 → 500） | **两边都没有** |
| 身份证号唯一性 | ❌ 不查重 | ✅ `store_people` + `Person.card` UNIQUE | 仅后端 |

**结论**：除"身份证唯一性"一条外，**所有字段级限制都只有前端一层**。前端被绕过（直接调 API、开发者工具改值、并发提交）时，脏数据畅通无阻地入库。本方案处理其中的**格式类**部分。

### 两处"前端放行、后端拒或崩"的真实撞车（本方案必须消掉）

**撞车 ①：名单内身份证重复，前端完全不查。**
用户填完 60 行点提交，才被后端拒：「该身份证已被使用，请检查您的身份证和姓名是否输入正确」。而且后端的现行语义很绕：

- 同 `card` **不同名** → 拒
- 同 `card` **同名** → **放行**（两条 `report_person` 指向同一条 `person` 记录）
- 同 `card` 在库里被别校的人用过且名字不同 → 拒

也就是说，**同一个人可以在同一支乐团里出现两次并提交成功**。这是脏数据。

**撞车 ②：年龄填小数或科学计数法，后端 500。**
人员的年龄框是 `type="number"` 且**没有任何输入过滤**，浏览器允许敲进 `12.5` / `1e5`（`type="number"` 认为二者都是合法数值）。前端只判非空就放行 → 后端 `Person.age` 是 `IntegerField`，`int("12.5")` 抛 `ValueError` → 视图无 `try/except` → **HTTP 500**，用户看到通用错误、数据未保存。反向的 `-3` 则被后端照存不误。

## 三、"保证一样"的机制

只写"两边都用这个正则"是保证不了的。本方案用三层：

### 3.1 第一层：规则清单（同源，逐字相同）

两侧各有一个镜像文件，**导出一份内容完全相同的字符串清单**：

- 前端 `src/config/fieldRules.js`
- 后端 `apps/api/field_rules.py`

```js
// 前端 src/config/fieldRules.js
/**
 * 【同源声明】本清单与后端 apps/api/field_rules.py 的 RULE_MANIFEST 必须逐字相同。
 * 改任何一条必须同时改两处；跑 `npm run check:rules` 可自动比对（见第七节）。
 * 清单之外不允许再出现第二份正则或第二份文案。
 */
export const RULE_MANIFEST = [
  ['RE_CARD',           '^\\d{17}[\\dXx]$'],
  ['RE_PHONE',          '^1[3-9]\\d{9}$'],
  ['RE_LANDLINE',       '^0\\d{2,3}-?\\d{7,8}$'],
  ['RE_DIGITS',         '^\\d+$'],
  ['AGE_MIN',           '1'],
  ['AGE_MAX',           '120'],
  ['MSG_CARD',          '身份证号格式不正确，应为18位'],
  ['MSG_PHONE',         '手机号或座机格式不正确'],
  ['MSG_AGE_NOT_INT',   '年龄只能是数字'],
  ['MSG_AGE_RANGE',     '年龄需在1-120之间']
]
```

```python
# 后端 apps/api/field_rules.py
"""【同源声明】本清单与前端 src/config/fieldRules.js 的 RULE_MANIFEST 必须逐字相同。"""
RULE_MANIFEST = [
    ['RE_CARD',         r'^\d{17}[\dXx]$'],
    ['RE_PHONE',        r'^1[3-9]\d{9}$'],
    ['RE_LANDLINE',     r'^0\d{2,3}-?\d{7,8}$'],
    ['RE_DIGITS',       r'^\d+$'],
    ['AGE_MIN',         '1'],
    ['AGE_MAX',         '120'],
    ['MSG_CARD',        '身份证号格式不正确，应为18位'],
    ['MSG_PHONE',       '手机号或座机格式不正确'],
    ['MSG_AGE_NOT_INT', '年龄只能是数字'],
    ['MSG_AGE_RANGE',   '年龄需在1-120之间']
]
```

**为什么是"字符串清单"而不是直接写正则/常量**：两份文件的语法不同（JS 字面量 vs Python `r''`），直接对比源码必然不等。把 `key → 值字符串` 抽成统一形态后，才可能做机器比对。工作用的 `RegExp` / `int` 一律由清单派生：

```js
const R = Object.fromEntries(RULE_MANIFEST)
export const RE_CARD     = new RegExp(R.RE_CARD)
export const RE_PHONE    = new RegExp(R.RE_PHONE)
export const RE_LANDLINE = new RegExp(R.RE_LANDLINE)
export const RE_DIGITS   = new RegExp(R.RE_DIGITS)
export const AGE_MIN     = Number(R.AGE_MIN)
export const AGE_MAX     = Number(R.AGE_MAX)
```

```python
_R = dict(RULE_MANIFEST)
RE_CARD     = re.compile(_R['RE_CARD'])
RE_PHONE    = re.compile(_R['RE_PHONE'])
RE_LANDLINE = re.compile(_R['RE_LANDLINE'])
RE_DIGITS   = re.compile(_R['RE_DIGITS'])
AGE_MIN     = int(_R['AGE_MIN'])
AGE_MAX     = int(_R['AGE_MAX'])
```

这样**清单是唯一可改的地方**，派生代码不需要动，两侧也不可能各改各的。

### 3.2 第二层：单一校验入口

前端的同一个规则出现在 **5 个执行点**（`OrchestraForm` 的 rules、`PersonTable` 的 `checkLine`/`exportCheck`、`TeacherTable` 的 `checkLine`、各输入框的过滤）。**这些点全部调用 `fieldRules.js` 的函数，一处都不许内联正则**：

```js
export function checkCard(v)   // → { ok: false, msg: '身份证号格式不正确，应为18位' }
export function checkPhone(v)  // → { ok: false, msg: '手机号或座机格式不正确' }   手机号 OR 座机，二者之一即通过
export function checkAge(v)    // → { ok: false, msg: '年龄只能是数字' | '年龄需在1-120之间' }
```

后端同理，`store_people` 与 `create_report`/`update_report` 都调 `field_rules.py` 的 `check_card/check_phone/check_age`。

### 3.3 第三层：可比对脚本（真正的"保证"）

`scripts/check-field-rules.mjs`：从两侧文件里抽出 `RULE_MANIFEST`，逐条严格相等比对，任一不等即打印差异并 `exit 1`。

```
node scripts/check-field-rules.mjs                 # 默认后端目录 ../yilinbei
BACKEND_DIR=/path/to/yilinbei node scripts/check-field-rules.mjs
```

- 后端目录不存在时**打印警告并跳过**（不阻断前端开发），退出码 0
- 挂进 `package.json`：`"check:rules": "node scripts/check-field-rules.mjs"`
- 建议同时挂到两侧的提交前检查（前端 husky 或 CI；后端 pytest 里加一条等价的断言）

## 四、数字相关输入位置（专项设计）

这是本次风险最集中的一块。先把报名端所有"数字相关"的输入位置列全：

| # | 位置 | 字段 | 现状控件 | 现状输入过滤 | 现状校验 |
|---|---|---|---|---|---|
| N1 | `OrchestraForm.vue` 作品总时长-分 | `minute` | `type="number"` | `value.replace(/\D\|^-1/g,'')` | 必填；正整数；0–60；≤ 类型+组别上限 |
| N2 | `OrchestraForm.vue` 作品总时长-秒 | `second` | `type="number"` | 同上 | 必填；正整数；0–60 |
| N3 | `PersonTable.vue` 年龄 | `age` | `type="number"` | **无** | **只判非空** |
| N4 | `TeacherTable.vue` 年龄 | `age` | `type="number"` | **无** | **只判非空** |
| N5 | 两张表 身份证号 | `card` | `type="text"` | 无 | 只判非空 |
| N6 | 两张表 联系电话 | `phone` | `type="text"` | 无 | 只判非空 |
| N7 | `OrchestraForm.vue` 领队电话 | `contact_phone` | `type="text"` | 无 | 只判非空 + 长度 1–20 |

> **N5–N7 必须保持文本类型**，不要"顺手统一成 number"。原因：前导 0 会被吃掉、末位 `X` 无法输入、超过 15 位的整数在 JS 里丢精度。它们是"数字串"，不是"数字"。

### 4.1 `type="number"` 的四个陷阱（N1–N4 现状）

**陷阱 1 · 非法值让整个输入框被清空。**
`<input type="number">` 在内容不是合法数值时，`.value` 返回**空串**。用户已有 `12`，再敲一个 `e`（`e` 在 number 框里被浏览器接受）→ 值变成 `12e`（非法）→ `.value === ''` → `oninput` 里的 `replace` 拿到空串、返回空串 → **输入框变空，前面的 12 没了**。

**陷阱 2 · 合法小数 / 科学计数法被静默篡改。**
`12.5` 是合法 number，`.value === '12.5'` → `/\D/g` 删掉 `.` → 变成 **`125`**。
`1e5` 同理 → 变成 **`15`**。
用户想填 12，提交的是 125 —— 这不是"帮用户过滤"，是**静默改数据**。时长框上 `12.5` → `125` 会被上限校验拦住（用户一头雾水）；`1e5` → `15` 在中学组（≤15）**能直接通过**。

**陷阱 3 · 滚轮改值。**
Chrome 下 `type="number"` 获得焦点后，滚轮会增减数值。页面滚动经过时长框，值被悄悄改掉。本仓没有任何隐藏 spinner 的 CSS（`src/styles/` 下无 `-webkit-inner-spin-button` 规则），所以这个行为当前是活的。

**陷阱 4 · 同一字段两种类型，「0」的结论相反。**
`v-model` 不加 `.number`，界面填的 `age` 是字符串 `"12"`；Excel 导入时 `age` 来自 xlsx，是数字 `12`。
判空写的是 `!item.age` —— 对字符串 `"0"` 为**假**（放行），对数字 `0` 为**真**（报"年龄不能为空"）。
即：**0 岁在界面填能过，从 Excel 导入会报错**。同一个值两种结论 —— 验收时同一份名单，界面手填和 Excel 导入会得到相反结论，属于最难解释的一类 bug。

> **修完之后这一条被彻底消除**：D6 改成显式判空（`v === '' || v == null`）后两条路径对 `0` 的结论一致（都是"非空、进入范围校验"），R3 的 1–120 再一致地把它判为超范围。**但类型偏移本身没消失** —— `age` 仍是"界面是字符串、导入是数字"，所以 `checkAge` 内部必须先 `String(v)` 再匹配正则，且提交前要 `Number()` 归一（F15）。验收时**界面手填与 Excel 导入两条路径都要各过一遍**。

### 4.2 规范 D（对 N1–N4 四个数字框统一适用）

| 编号 | 规定 | 消掉的陷阱 |
|---|---|---|
| **D1** | 控件改 `type="text"` + `inputmode="numeric"`，**不再用 `type="number"`**。`inputmode="numeric"` 保证手机端仍弹数字键盘。 | 1、3 |
| **D2** | 键盘层拦截：`@keydown` 放行「数字键 + 编辑键 + Ctrl/Meta 组合键」，其余 `preventDefault`。放行组合键是为了不挡 `Ctrl+V`/`Ctrl+A`。**这是"拒绝输入"而不是"清洗输入"**。 | 2 |
| **D3** | 输入层兜底：`@input` 中整串不匹配 `^\d*$` 时剥离非数字字符。**D2 挡不住的路径**（输入法上屏、拖拽文本、浏览器自动填充）由这里兜——这些路径的值不是用户逐键敲的，剥离是安全的。 | 2 |
| **D4** | 长度限制：`maxlength`（年龄 `3`、分钟 `2`、秒 `2`）。挡在原生层，连快速连打都进不来。 | — |
| **D5** | **校验器是主闸，不是兜底。** D2/D3 只优化输入体验，绕得过去（开发者工具改值、直接调 API），所以必须同时有校验器，且与后端共用同一清单。 | 全部 |
| **D6** | 类型归一：`age` 判空改成显式判空 `v === '' \|\| v == null`，**不再用 `!item.age`**；提交前 `age` 转 `Number`。 | 4 |

**D2 的实现（共享，四个框用同一个函数）**：

```js
// src/config/fieldRules.js
const NAV_KEYS = ['Backspace','Delete','Tab','Enter','Escape',
                  'ArrowLeft','ArrowRight','ArrowUp','ArrowDown','Home','End']

/** 键盘层拒绝非数字。Ctrl/Meta/Alt 组合键一律放行（否则挡掉粘贴与全选） */
export function blockNonDigit(e) {
  if (e.ctrlKey || e.metaKey || e.altKey) return
  if (NAV_KEYS.includes(e.key)) return
  if (!/^\d$/.test(e.key)) e.preventDefault()
}

/** 输入层兜底：整串不合法则剥离非数字（拦输入法/拖拽/自动填充） */
export function stripNonDigit(v) {
  const s = v == null ? '' : String(v)
  return /^\d*$/.test(s) ? s : s.replace(/\D/g, '')
}
```

模板（以 `PersonTable` 年龄为例）：

```html
<el-input
  v-model="item.age"
  type="text"
  inputmode="numeric"
  maxlength="3"
  placeholder="请输入年龄"
  @keydown="blockNonDigit"
  @input="item.age = stripNonDigit(item.age)"
/>
```

> **`@keydown` / `@input` 能落到原生 input 上**：`el-input` 会把未声明的 `onKeydown`/`onInput` 透传到内部 `<input>`（本仓 `OrchestraForm` 的 `oninput="..."` 用的就是同一条路径）。

**D1 的可见副作用（需你在浏览器确认一眼）**：`type="text"` 与 `type="number"` 的原生渲染有差异 —— number 框在 Chrome 下悬停/聚焦时显示上下微调箭头，本仓没有隐藏它的 CSS，所以改成 text 后**箭头会消失**。这将是一处可见变化（属于修掉陷阱 3 的副产物）。若要保留箭头，只能退回保留 `type="number"`，而陷阱 1（清空整框）**无法消除** —— 不建议。

### 4.3 数字字段的校验顺序（顺序即优先级）

`checkLine` / `exportCheck` / `minuteValidator` 都是 if 链，**第一个不通过的即为提示**。数字字段的插入位置固定为「非空 → 格式 → 范围」：

| 字段 | 顺序 |
|---|---|
| `minute`（N1） | 必填 → 正整数 → 上限（类型×组别） → ≤60 |
| `second`（N2） | 必填 → 正整数 → ≤60 |
| `age`（N3/N4） | 非空 → 只能是数字 → 1–120 |
| `card`（N5） | 非空 → 18 位格式 → （名单内查重，见 R4，在合并后单独判） |
| `phone`（N6/N7） | 非空 → 手机号或座机格式 |

`minute` 的现有校验顺序（`value===''` → `second===''` → 分钟正整数 → 秒正整数 → 上限 → 0–60）**逐字保留不动**，本次只补数字输入规范。

## 五、规则定义（唯一来源）

| 编号 | 字段 | 规则 | 文案 | 两侧实现位置 |
|---|---|---|---|---|
| **R1** | `card` 身份证号 | `.trim()` 后匹配 `^\d{17}[\dXx]$` | `身份证号格式不正确，应为18位` | 前端 `checkCard`；后端 `check_card` |
| **R2** | `phone` / `contact_phone` | `.trim()` 后匹配 `^1[3-9]\d{9}$` **或** `^0\d{2,3}-?\d{7,8}$`（二者之一即通过） | `手机号或座机格式不正确` | 前端 `checkPhone`；后端 `check_phone` |
| **R3** | `age` 年龄 | `^\d+$` 且 `1 ≤ n ≤ 120` | `年龄只能是数字` / `年龄需在1-120之间` | 前端 `checkAge`；后端 `check_age` |
| **R4** | 名单内 `card` | 同一份提交里 `.trim().toUpperCase()` 后不得重复 | `第{甲}行与第{乙}行的身份证号重复` | 前端 `findDuplicateCard`；后端 `store_people` |

### 5.1 R1 的两条边界（已拍板）

**(a) 只判「长度 + 字符集」，不验校验位，不放 15 位旧号。**
GB 11643 的加权算法可以实现，但不做。理由：① 算法要在两个仓库各写一遍、两处都要对，收益是一条**连报错都说不清的规则**（提示"格式不正确"，用户对照自己的身份证怎么看都对，实际是校验位不符）；② 真正挡住冒名的是资格审核（BE-04），不是校验位；③ 存量数据若大量不符，编辑页会被全部拦死（见第八节）。

**口径已定：`^\d{17}[\dXx]$` 一条正则走到底** —— 不验校验位、不放 15 位、不分身份。这带来两个必须一起处理的后果：

- **15 位旧号会被拦。** 若存量里有（第八节 SQL 第 1 条能查出来），这些学校在编辑页会被卡住，必须改成 18 位。这是"选严格"的已知代价，不是 bug。
- **`X` 大小写必须归一化**（见下条 (b)），因为 `[\dXx]` 两个都放行，不归一就会绕过查重。

**(b) X 必须归一化。**
末位 `x` 小写与 `X` 大写是同一个号，但 `Person.card` 是 UNIQUE、后端比对又是字符串相等。若 A 填 `...x`、B 填 `...X`，后端查不到已存在的那条 → 走 create → UNIQUE 冲突 → 500。
所以两侧统一在**校验与比对前 `.trim().toUpperCase()`**；写入时也用归一化后的值（对应第六节 §6.2 的后端必改项）。

### 5.2 R2 的两条口径

**(a) 手机号字面量会与 `/online` 端重复一处。**
[LeaderTable.vue:239](../src/components/online/LeaderTable.vue#L239) 已有 `/^1[3456789]\d{9}$/`，与 `[3-9]` 语义相同、字面量不同。本次把新规则集中在 `fieldRules.js`，**online 端不动**（另一场活动、路由已摘）。这意味着全仓会存在两个字面量 —— 取舍已说明；要收敛，就去改 LeaderTable 那 1 行。

**(b) 座机分支的写法：可选连字符，不做区号白名单。**

```
^0\d{2,3}-?\d{7,8}$
```

- 区号只要求"0 开头、3~4 位"（`010` 到 `0xxx` 都放行），**不列城市白名单**。列白名单等于把一份会过期的城市代码表放到两个仓库里各自维护，收益为零。
- 连字符 `-` 可选，因为「028-88888888」和「02888888888」是同一个号，收两种写法就少一类投诉。
- **不做长度 11 的硬判**：座机长度本身就随区号变化（10 位或 11 位），拿手机号的 11 位去要求它会把「028-8888888」这类正常号拦掉。
- **不做纯数字兜底**（如 `^\d{10,11}$`）：会放行「12345678901」这种明显不是电话的东西，反而让"格式不正确"这条提示失去意义。宁可让用户补个区号。

### 5.3 R4 与后端现状的差异（必须后端点头）

后端现行是「同 `card` **同名放行**、不同名才拒」（[services.py:96-100](file:///d:/yl-all/yilinbei/apps/core/services.py)）。**要"两边一样"必须收紧为「同 `card` 出现两次即拒，不看名字」**，否则前端会拦下后端本来放行的数据 —— 那就是新的不一致。
收紧后 `names_by_card[card] != name` 那个判据可以删掉，因为 `card in names_by_card` 本身就该拒了。

### 5.4 跨表重复只有"合并后"才看得见

后端 `store_people` 收到的 `people` 是 `t.person` —— 即前端 `onSubmit` 里拼好的 `allPeople`（教师在前、人员在后）。**指导教师表里的人和参演人员表里的人同号，只有把这个数组合并后才看得见**。所以 R4 的检查点必须在 `allPeople` 组装完成之后，两张表各自查会漏掉这一类。行号也用合并后的下标 +1，与后端报错的行号同口径。

### 5.5 归属：每一条规则放在哪一端

"两边都写一遍"不是目的，**"同一个值在哪一端被拦住时结论一致"**才是目的。所以每条规则先定归属，再谈实现。四条准则：

| 准则 | 内容 | 推论 |
|---|---|---|
| **P1 · 单个值的格式/范围** | 前端给用户即时反馈，后端是数据闸门，**两侧必须同源同做** | 只做一端 = 留一条绕过路径（绕前端 → 脏数据；只做前端 → 后端 500 / 存任意值） |
| **P2 · 跨记录 / 唯一性 / 并发 / 状态** | **只能后端做**。前端查重只是"提前告知"，永远替代不了后端（两个标签页、两台机器同时提交，前端各查各的都是干净的） | 这类规则前端**必须有**但性质是"提示"，后端才是"判定" |
| **P3 · 即时输入反馈** | 输入框该不该接受这个按键、滚轮会不会改值、输入法上屏后长什么样 —— **纯前端**，后端没有对应概念 | 后端不为体验做校验，前端不为体验改后端 |
| **P4 · 后端改动风险大** | 需动 `Report`/`Person` 模型（迁移）、动 `transaction.atomic` 结构、或要重建一张规则表 → **本批由前端承担**，并在本节表格里登记为「已知单侧规则」，写清后端补齐的前置条件 | 前端承担 = 承认这条规则可被绕开；登记的目的是**不假装它已经对齐了** |

## 七、一致性保障机制的落地细节

### 7.1 比对脚本

```js
// scripts/check-field-rules.mjs
/**
 * 校验前后端的字段规则清单是否逐字相同
 *
 * 用法：node scripts/check-field-rules.mjs
 *      BACKEND_DIR=/path/to/yilinbei node scripts/check-field-rules.mjs
 * 退出码：0 = 一致或后端目录缺失（不阻断前端开发）；1 = 存在不一致
 */
```

- 默认后端目录 `../yilinbei`（相对 `scripts/`）
- 从 `src/config/fieldRules.js` 抽出 `RULE_MANIFEST`：匹配 `^\s*\['(\w+)',\s*'((?:[^'\\]|\\.)*)'\]` 形式的行
- 从 `apps/api/field_rules.py` 抽出同名清单：同样的正则，额外容忍 `r` 前缀
- 逐条比对 `key` 与 `value`；**先按 key 对齐**（顺序不同不算不一致），只报值不同或 key 缺失
- 输出格式：「RE_PHONE: 前端 `^1[3-9]\d{9}$` ≠ 后端 `^1[3456789]\d{9}$`」
- 后端目录不存在 → `console.warn('后端目录不存在，跳过清单比对')`，`exit 0`

### 7.2 为什么这比"写注释要求同步"可靠

注释只能提醒人，不能阻止人。清单比对把"两边一样"变成一个**可执行的断言** —— 改了一侧忘了另一侧，`npm run check:rules` 立刻失败。这也是本方案唯一能兑现"**保证**一样"的部分；前五节的表格只是描述，第七节才是机制。

## 八、上线前必须做的存量数据核查

加格式校验的直接后果：**编辑页会拦下历史数据**。存量库里凡格式不符的记录，用户打开编辑页会看到红字且**无法保存**，必须改成合规值。所以先跑统计，用真实数字决定要不要分批放开。

GaussDB / PostgreSQL：

```sql
-- 1) 身份证：全局 person 表（跨所有活动）
SELECT count(*) FILTER (WHERE card !~ '^[0-9]{17}[0-9Xx]$') AS 格式不符,
       count(*) FILTER (WHERE card ~ '^[0-9]{17}[0-9Xx]$')  AS 合规,
       count(*) FILTER (WHERE card ~ '^[0-9]{15}$')         AS 十五位旧号,
       count(*) FILTER (WHERE card ~ '^[0-9]{17}x$')        AS 小写x结尾,
       count(*) FILTER (WHERE card <> btrim(card))          AS 首尾有空格,
       count(*) AS 总数
FROM person;

-- 2) 人员联系电话（手机号 或 座机 都算合规）
SELECT count(*) FILTER (WHERE coalesce(phone,'') <> ''
                          AND phone !~ '^1[3-9][0-9]{9}$'
                          AND phone !~ '^0[0-9]{2,3}-?[0-9]{7,8}$') AS 格式不符
FROM person;

-- 3) 领队电话（口径同上）
SELECT count(*) FILTER (WHERE contact_phone !~ '^1[3-9][0-9]{9}$'
                          AND contact_phone !~ '^0[0-9]{2,3}-?[0-9]{7,8}$') AS 格式不符
FROM report;

-- 4) 年龄（新口径 1–120）
SELECT count(*) FILTER (WHERE age IS NOT NULL AND (age < 1 OR age > 120)) AS 超范围,
       count(*) FILTER (WHERE age IS NOT NULL AND age < 0)                AS 负数,
       count(*) FILTER (WHERE age IS NOT NULL AND age BETWEEN 1 AND 120)  AS 合规
FROM person;

-- 5) 名单内重复身份证（同一份报表里同号出现两次）
SELECT report_id, count(*) AS 次数
FROM report_person rp
JOIN person p ON p.id = rp.person_id
WHERE rp.deleted_at IS NULL
GROUP BY report_id, p.card
HAVING count(*) > 1;
```

MySQL（若存量在原 Laravel 库）把 `!~` → `NOT REGEXP`、`~` → `REGEXP`、`btrim` → `TRIM`。

**判读口径**：

| 结果 | 动作 |
|---|---|
| 身份证 `格式不符 = 0` | 直接上，无风险 |
| `格式不符 > 0` 且占比 < 1% | 上线，但把 SQL 结果**按学校列出来**，由委员会通知对应学校修改（比写兼容代码便宜） |
| `格式不符` 占比高 | 说明这套规则在往届根本不成立 → 需重新拍板，可能得退到"只判非空 + 长度不超过 18"的宽松版 |
| `十五位旧号 > 0` | **这些号会被 R1 拦死**（5.1(a) 已定不放 15 位）。数量少 → 通知学校改成 18 位；数量多 → 回来重开 5.1(a)，把 `RE_CARD` 改成 `^\d{15}$\|^\d{17}[\dXx]$` |
| `小写x结尾 > 0` 或 `首尾有空格 > 0` | **必须先做完 B2 的归一化**，否则这些学校的编辑页会 500 |
| 第 5 条有结果 | 存量里有"同一人在同一支乐团出现两次"，这些报表在编辑时会被 R4 拦住 |

**这组数字目前拿不到**（本机连不上库；后端 `MIGRATION_GAPS.md` 也记着"生产 schema 快照未提供"），必须由你或后端跑。
