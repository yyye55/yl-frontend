## 零、为什么「搜索框」这件事值得单独写一份文档

因为在这个项目里，「搜索框」**不是一个功能，而是十个互不共用的实现**，
分布在 6 个后端函数里，匹配字段各不相同。

甲方说「搜索框搜不出东西」时，**不会指明是哪一个框**。
前端也无法用统一文案写 placeholder —— 因为十个框能搜的列根本不一样。
只有把这张表给全，才能避免「改了一个框、另一个框还是搜不到」。

## 一、P0 · 管理员端组别下拉的值，后端一个都不认

> **本节结论：后端不需要改任何一行代码。修复责任全在前端。**
> 之所以写进这份「后端方案」，是因为它必须**先被后端确认**才能改 ——
> 见 1.4 的三个待确认问题。

### 1.1 现象

管理员端 `/admin/report`（报名列表）页面，**组别下拉框选中任意一项 → 列表恒为空**。

### 1.2 根因（已逐字核实，非推断）

**前端** `src/views/admin/report.vue:62-75` 的组别下拉，五个值是：

```
管乐团-小学组 / 管乐团-中学组 / 管乐团-大学组
铜管乐团-小学组 / 铜管乐团-中学组
```

**后端**对组别的认知，全仓库一致是**旧值**：

| 位置 | 代码 | 值 |
|---|---|---|
| `views.py:509-510` `stats_admin` | `for group, name in (("小学组",…),("中学组",…),("大学组",…))` | 旧值 |
| `views.py:949` `scoped_total(city)` | `groups = [("小学组","小学组"),("中学组","中学组")]` | 旧值 |
| `views.py:956` `scoped_total(school)` | `group="大学组"` | 旧值 |
| `core/report_drafts.py:46` `REPORT_ALLOWED_GROUPS` | `{5: ("小学组","中学组")}` ← **写入侧白名单** | 旧值 |
| `api/export_services.py:97` `group_number` | `{"小学组":1,"中学组":2,"大学组":3}` | 旧值 |
| `api/registration_form.py:260` | `_checkline(("小学组","中学组","大学组"), report.group)` | 旧值 |
| `migrations/0007_db_comments.py:64` | `"group": "节目组别：小学组 / 中学组 / 大学组"` | 旧值 |

**核实方法**：`apps/` 全目录 grep `管乐团-小学组` 与 `铜管乐团-小学组` ——
**零命中**。（`registration_form.py:259` 那个 `("管乐团","铜管乐团")` 元组是
`establishment` 乐团**类型**的候选值，不是 `group`；`personRules.js` 里的
`orchestraType`/`level` 同理，是 `establishment` 与 `group` 的组合规则。）

而 `report_queryset`（`views.py:122-124`）是**精确匹配**：

```python

        qs = qs.filter(group=request.GET.get("group"))
```

**⇒ `group=管乐团-小学组` 打过去，库里不存在这个值 → 恒空。**

## 二、P1 · 三处能力缺口

### 2.1 【P1-1】现场展演：搜不到「合唱团名称」和「联系人」

**接口**：`/api/live/list`（`live_list` → `live_page`）、`/api/committee/online/list`

**现状**（`views.py:244-246`）只匹配一个字段：

```python
    keyword = request.GET.get("keyword")
    if keyword:
        qs = qs.filter(name__icontains=keyword)
```

**而这两页的表格有 4 列**（`views/online/list.vue:47-58`、`views/committee/online.vue:89-93`）：

| 列 | 字段 | 现在能搜？ |
|---|---|---|
| 合唱团名称 | `choir_name` | ❌ |
| 节目名称 | `name` | ✅ |
| 组别 | `group` | ❌（**故意，见下**） |
| 联系人 | `contact_name` | ❌ |
| 联系电话 | `contact_phone` | ❌（**故意，见下**） |

**症状**：在这两页搜乐团名或联系人 → 列表瞬间清空 → 用户报「搜索框坏了」。

**为什么前端没敢改 placeholder**：这两页的 placeholder 至今仍写「请输入内容」，
正是因为后端确实搜不到那些列。

**两个字段为什么不入 `keyword`**：

- **`group`** 是固定枚举（`小学组/中学组/大学组` 等少数值），
  用输入框投组名不自然，仍应由下拉框负责。
- **`contact_phone`** 是纯数字串，用 `icontains` 搜会出现「搜 `123` 命中一堆无关记录」，
  而且**电话号码片段极易误命中**（如搜 `1380` 命中所有 1380 开头的人），
  属于典型的「假阳性比漏命中更伤」的字段。

### 2.2 【P1-2】用户管理：搜不到「修改人姓名」和「其他信息」

**接口**：`/api/{admin,committee}/user/list`（`user_list`，`views.py:573-585`）

**现状**已覆盖三列（这部分是对的）：

```python
    if keyword: qs = qs.filter(Q(username__icontains=keyword) | Q(tel__icontains=keyword) | Q(nickname__icontains=keyword))
```

**而 `views/admin/user.vue:106-184` 的表格共 6 列**：

| 列 | 字段 | 现在能搜？ |
|---|---|---|
| 账号 | `username` | ✅ |
| 名称 | `nickname` | ✅ |
| 类型 | `type` | ❌（枚举，由下拉负责） |
| 修改人姓名 | `leader` | ❌ **缺口** |
| 修改人电话号码 | `tel` | ✅ |
| 其他信息（备注） | `description` | ❌ **缺口** |

**症状**：想按备注内容找人、或查「某人经手的账号」→ 搜不到。

**顺带一个死参数**：`user_list` 还认一个独立的 `nickname` 参数
（`views.py:579-580`），而 `keyword` 的 OR 里**本来就有 `nickname`**。
⇒ 这个参数**现在只会被历史请求或外部调用触发**，前端已不再发送。
**建议保留但加注释说明**（删掉会让外部调用静默失去该能力），**不属本次必改项**。

### 2.3 【P1-3】操作日志：搜不到「操作账号」

**接口**：`/api/admin/log/list`（`admin_log_list`，`views.py:779-787`）

**现状**只匹配正文：

```python
    if request.GET.get("keyword"): qs = qs.filter(content__icontains=request.GET["keyword"])
```

**而 `views/admin/log.vue:58-59` 的表格有 2 列**：内容 `content`、操作账号 `user.nickname`。
**操作账号搜不到。** 典型症状：想查「某人今天做了什么」→ 搜不到。

**⚠️ 这一处最容易改错**：`Logs` 模型（`models.py:352-362`）只有
`id / user_id / type / content / created_at / updated_at`，
**只有 `user_id` 一个整数列，没有指向 `User` 的外键**。
所以**绝不能写** `Q(user__nickname__icontains=...)` —— 那会直接抛
`FieldError: Cannot resolve keyword 'user' into field. Choices are: ...`。
必须用 `user_id__in` 子查询。详见 4.3。

## 三、P2 · 导出不受搜索约束（**需产品确认，不是缺陷**）

### 3.1 现象

「用户管理」页输入搜索词 → 列表剩 3 条 → 点「导出数据」→ **Excel 里是全部账号**。

### 3.2 根因

`user_export_admin`（`views.py:734-740`）**一个筛选条件都不读**：

```python
def user_export_admin(request, show_committee=False):
    qs = User.objects.filter(type__in=ADMIN_USER_TYPES if show_committee else COMMITTEE_USER_TYPES)
    rows = [["账号", "名称", "密码", "修改人姓名", "修改人联系方式", "备注"]]
    rows += [[x.username, x.nickname, "初始密码为scylb@2026", x.leader, x.tel, x.description] for x in qs]
```

列表页的 `keyword` 与 `type` 两个筛选，**导出时全部失效**。
`committee_export_data`（`:878-895`）与 `export_data`（`:444-451`）只认 `group`，同样不认 `keyword`。

### 3.3 建议

| 接口 | 现在认的筛选 | 建议新增 |
|---|---|---|
| `/api/{admin,committee}/user/export` | —— | `keyword`（与列表同口径）、`type` |
| `/api/committee/export/data` | `group` | `keyword` |
| `/api/export/data` | `group` | `keyword` |

**口径要求**：导出必须与列表**同口径**。
否则会出现「列表 3 条、导出 500 条」—— 与现在的问题正好是同一类错位，只是方向相反。

**过渡期建议（前端可先做，不依赖后端）**：
导出时若当前有筛选条件，弹提示「导出内容不受当前筛选影响」；
后端支持后直接删掉这个提示。

> **本节待甲方/组委会确认后再动手**，确认前不要写代码。

## 四、逐条 patch

### 4.1 【P1-1】`live_page`：补 `choir_name` / `contact_name`

**位置**：`apps/api/views.py:244-246`

```diff
     keyword = request.GET.get("keyword")
     if keyword:
-        qs = qs.filter(name__icontains=keyword)
+        # 现场展演页表格显示 4 列（合唱团名称 / 节目名称 / 组别 / 联系人），
+        # 原来只匹配 name，按乐团名或联系人搜会整表清空。
+        # group 与 contact_phone 故意不入 keyword：前者是枚举、应由下拉负责；
+        # 后者是数字串，icontains 极易误命中（搜 "1380" 命中所有 1380 开头的记录），
+        # 假阳性比漏命中更伤。
+        qs = qs.filter(
+            Q(name__icontains=keyword)
+            | Q(choir_name__icontains=keyword)
+            | Q(contact_name__icontains=keyword)
+        )
```

**字段存在性已核对**（`apps/core/models.py:406-422` `LiveReport`）：
`name` / `choir_name` / `contact_name` 均为 `CharField(max_length=255, default=" ")`。

**为什么不丢行（与 `admin_person_list` 那次实测同源）**：
若存量数据里这三列有 `NULL`（老数据绕过 `default` 直插），
`NULL LIKE %k%` 求值为 `NULL`，该行只是**不走这一支**，
而 `name` 一支照常命中 ⇒ **不丢行**。

### 4.2 【P1-2】`user_list`：补 `leader` / `description`

**位置**：`apps/api/views.py:577-580`

```diff
     qs = User.objects.filter(type__in=allowed_types).order_by("id"); keyword = request.GET.get("keyword")
-    if keyword: qs = qs.filter(Q(username__icontains=keyword) | Q(tel__icontains=keyword) | Q(nickname__icontains=keyword))
+    if keyword:
+        # 用户管理页表格显示 6 列，其中「修改人姓名」与「其他信息」两列原来搜不到，
+        # 按这两列的内容搜会整表清空。type 是枚举、仍由下拉负责。
+        qs = qs.filter(
+            Q(username__icontains=keyword)
+            | Q(tel__icontains=keyword)
+            | Q(nickname__icontains=keyword)
+            | Q(leader__icontains=keyword)
+            | Q(description__icontains=keyword)
+        )
```

**字段存在性已核对**（`apps/core/models.py:120-122` `User`）：
`description`（`max_length=1000`）、`leader`（`max_length=50`）
均为 `CharField(null=True, blank=True)` ⇒ 允许 `NULL`，同样不丢行。

**一个必须记录的可预期副作用**：
这次扩面会让**原本查不到的行变得查得到**。
与《后端修改说明-可报两支（can_report_twice）.md》里写的
「不会让任何原本能查到的结果消失」同源 —— `Q` 是「或」，**只会变多、不会变少**。
唯一可预期的副作用：搜一个既是账号名又是备注片段的词时，结果会变多 —— 这正是需求要的。

### 4.3 【P1-3】`admin_log_list`：补操作账号（**必须用子查询**）

**位置**：`apps/api/views.py:783-784`

```diff
     qs = Logs.objects.all().order_by("-created_at")
-    if request.GET.get("keyword"): qs = qs.filter(content__icontains=request.GET["keyword"])
+    if request.GET.get("keyword"):
+        # 日志页表格显示「内容」与「操作账号」两列，操作账号原来搜不到。
+        # 【关键】Logs 只有 user_id 一个整数列、**没有指向 User 的外键**，
+        # 所以不能写 Q(user__nickname=...)（会抛 FieldError），只能走子查询。
+        kw = request.GET["keyword"]
+        matched = User.objects.filter(
+            Q(username__icontains=kw) | Q(nickname__icontains=kw)
+        ).values("id")

```

**性能代价（如实说明，不给拍脑袋的数字）**：
`user_id__in (子查询)` 会多执行一次子查询。
日志表数据量增长后该接口的 P95 需要评估 —— **本文档给不出生产数据量，故不给数字**。
若日志量很大，建议改成短路写法：**先按 `content` 过滤；结果为空时再回退到按操作人过滤**。

## 七、不要做的事

**① 不要为了迁就前端下拉，给后端加「五个新值」的兼容分支。**

`Report.group` 的**写入侧唯一入口**是 `report_drafts.REPORT_ALLOWED_GROUPS`，
它写的是 `小学组/中学组/大学组`。若后端加一层「把 `管乐团-小学组` 也映射成
`小学组`」的兼容，会立刻产生一个**新的歧义**：`小学组` 同时对应管乐团与铜管乐团，
而 `group` 字段**本身不含乐团类型**（乐团类型在 `establishment` 字段）。
映射会让「铜管乐团-小学组」和「管乐团-小学组」塌缩成同一个值，
**统计（`stats_admin` 按 `group` 分组计数）会随之算错**。
⇒ **正确做法是改前端**；若真要按乐团类型筛，走 1.4 问题 2 的 `establishment` 独立参数。

**② 不要动 `report_queryset` 里已经改好的 `keyword` 三字段 OR。**

`a5db1fd` 那段是对的，`school_name` 已并入。
把它改回「按身份分两支」会直接让学校端搜不到学校名。

**③ 不要顺手删掉 `choir_name` / `school_name` 两个独立参数。**

它们与 `keyword` 是 **AND** 关系，解决的是「叠加筛选」而非「一个框搜更多字段」。
本仓库前端已不再传，但**外部调用与历史请求传了仍应生效**。
删掉会让这些调用**静默失去筛选能力**（不报错、只是筛不动），比留着更坏。

**④ 不要把 P2（导出）混进 P1 的提交。**

P2 待产品确认；混在一起会让一个待确认的需求绑上已确认的修复。

  以及**任何 `group` 相关的代码**（P0 的修复责任在前端）。
