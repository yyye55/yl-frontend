## 零、怎么读这份文档

### 触发原因

学校账号在「上传审核图」弹窗里**一个文件都没传**，点「确认上传」，接口返回：

```
HTTP 200
{ "code": 0, "msg": "修改成功!",
  "data": { "id": 1, "user_id": 2, "type": 0, "files": [], "status": 0, "remark": "" } }
```

`files` 是空数组却报「修改成功!」。前端负责人要求把这条链路查清并交后端处理。

> 一个细节：`msg` 是「**修改**成功!」而不是「新建成功!」，说明当时库里**那一行已经存在**——
> 所以这一发是**覆盖**（本节的 S-1），不是新建。是否真的覆盖掉了此前的审核图，光看这个响应
> 无法判断（取决于那一行原本是不是空的），但接口对这两种情况**没有任何区分和保护**。

### 结论一句话

**`POST /api/scan/cau` 对 `files` 不做任何校验，且是无条件覆盖。** 空数组不是「什么都没做」，
而是**把该行已存的审核图整份清空**，并且照样返回 `code: 0`。

## 二、S-1（P0）空数组会清空已存的审核图

### 症状

```
[15] 已有扫描件 → 再 POST {type:0, files:[]}
     提交前库中 files=[ [{'uid': 'u1', 'name': '盖章扫描件.pdf'}] ]
     HTTP 200  code=0  msg='修改成功!'
     提交后库中 files=[ [] ]
```

用户看到的是「上传成功！」，实际发生的是**审核图被抹掉**。

### 根因

[`apps/api/views.py:349-355`](../../yilinbeihou/apps/api/views.py#L349-L355)：

```python
@api.post("/scan/cau", auth=auth)
def scan_create_update(request):
    data = body(request); obj, created = ScanFiles.objects.get_or_create(user_id=request.auth.id, type=data.get("type"))
    for key in ("files", "status", "remark"):
        if key in data: setattr(obj, key, data[key])   # ← 无条件覆盖，不判空
    obj.save()
    return response(success("新建成功!" if created else "修改成功!", model_dict(obj)))
```

`files` 一旦出现在 body 里，就**整份替换**该行的 `files`，不区分「用户删光了」和「用户什么都没做」。

### 前端为什么能走到这一步（这条不是理论路径）

`UploadScanDialog.vue` 是 `/city/index` 与 `/school/index` 共用的「上传审核图」弹窗：

1. `open()`（[:259-273](../../yl-frontend/src/components/common/UploadScanDialog.vue#L259-L273)）会把**服务端已存的审核图预加载进 `fileList`**；
2. `removeSuccess()`（[:200](../../yl-frontend/src/components/common/UploadScanDialog.vue#L200)）允许用户逐个删掉；
3. 「确认上传」按钮原本**没有 `:disabled`**，`updateFile()`（[:236](../../yl-frontend/src/components/common/UploadScanDialog.vue#L236)）也**没有空列表判断**，直接发 `{type:0, files:[]}`。

所以：**打开弹窗 → 把预加载的已有审核图全删掉 → 点「确认上传」→ 服务端那一行被清空 → 界面弹「上传成功！」**，
全程没有任何二次确认（el-dialog 也没有「离开前确认」）。

### 为什么不能简单说「清空是用户自己点的」

后端目前**只有三个 scan 路由**：

```
apps/api/views.py:333  @api.get("/scan/list",  auth=auth)
apps/api/views.py:349  @api.post("/scan/cau",  auth=auth)
apps/api/views.py:358  @api.get("/scan/files", auth=auth)
```

**没有删除接口**。也就是说接口层面不存在「清空审核图」这个正当语义，
`files: []` 只能是误伤——前端拿不到「我确实想清空」这个意图，后端也不该把它当成一次合法更新。

## 三、S-2（P1）凭空建出一条空记录

```
[14] 全新用户 POST {type:0, files:[]}
     HTTP 200  code=0  msg='新建成功!'
     data.files=[]
     库里行数=1  files=[ [] ]
```

`get_or_create(user_id, type)` 会因为这一发空提交而**落库一条 `files` 为空的记录**。
后果是 `/api/scan/list?type=0`（[views.py:339-342](../../yilinbeihou/apps/api/views.py#L339-L342)）
按 `ScanFiles.objects.filter(type=...)` 的 `user_id` 过滤时，**这所学校会被算成「已上传」**，
组委会在列表里看到的是「有一份审核图」，点开却是空的。

## 四、S-3 / S-4 / S-5（P1、P2）`files` 与 `type` 都没有校验

### S-3　`files` 传什么存什么

```
[17] files 传非法值
     files=null        → HTTP 200 code=0 msg='新建成功!' 库中 files=[None]
     files='这不是数组' → HTTP 200 code=0                 库中 files=['这不是数组']
```

`ScanFiles.files` 是 `LegacyJSONField(null=True, blank=True)`（[`apps/core/models.py:305`](../../yilinbeihou/apps/core/models.py#L305)），
Django Ninja 层也没有 schema 校验，所以 JSON 里放什么就存什么。
前端 `UploadScanDialog.open()` 会无脑遍历 `res.data.data.files[i]`，遇到非数组会渲染出一堆空条目。

### S-4　`type` 非法 → 500

```
[不带 type]   → django.db.utils.IntegrityError: NOT NULL constraint failed: scan_files.type
[type=null]   → django.db.utils.IntegrityError: NOT NULL constraint failed: scan_files.type
[type='abc']  → builtins.ValueError: Field 'type' expected a number but got 'abc'.
[type=1.5]    → 不抛异常（会被存成 1）
```

三种非法输入都返回 **HTTP 500**，不是 400。
（与既有清单里的 **P2-2**「请求体不是对象 → 500」同一类问题：参数校验缺失，异常直接穿透到 500。）

### S-5　`type` 无白名单

```
[type=9（未定义渠道）] → HTTP 200 code=0 msg='新建成功!'  库中行数=1
```

`type` 是「渠道类型」（0 = 高校渠道 / 学校账号，1 = 市级渠道），目前是任意整数照建。

## 六、请后端怎么改

### 6.1 必做：拒绝空 `files`（修 S-1、S-2）

`files` **显式传空数组**时返回业务失败，不落库、不覆盖。沿用项目现有的 `failure()` 约定
（HTTP 200 + `code: 1`）：

```
POST /api/scan/cau
{ "type": 0, "files": [] }

→ HTTP 200
{ "code": 1, "msg": "请先上传文件", "data": null }
```

**关键：只拦显式空数组，不要顺手把「不带 files 键」也一起拦掉。** 探针 test_16 证明了两者语义不同：

```
[16] 对照：body 不带 files 键 → POST {type:0}
     实际 msg='修改成功!'  库中 files=[ [{'uid': 'u1'}] ]
     ✓ 不带 files 时确实不动该字段
```

现在的 `if key in data` 写法对「不带」的处理是**正确的**，问题**只**出在「显式传空」被当成一次正常更新。
所以最小改法是加一句校验，不要动现有循环：

```python
    if "files" in data and not data["files"]:
        return response(failure("请先上传文件"))
```

### 6.2 建议：`files` 加元素级校验（修 S-3）

至少要：是数组、非空、每项是对象且带 `url`。非法则 `code: 1` + 中文 `msg`，
不要让它原样落库（前端会按 `files[i].uid / .name / .url` 直接渲染）。

### 6.3 建议：`type` 加白名单 + 400（修 S-4、S-5）

- `type` 缺失 / 非整数 → **400 + 中文 msg**，不要再 500；
- `type` 限定在已定义的渠道集合内。

### 6.4 需要后端确认的一件事：是否要支持「清空审核图」

目前接口层面没有删除能力，前端弹窗里却能删光再提交，所以现状是「**能做，但只以误伤的方式做**」。

两个方向，请后端选一个并告知前端：

- **方向 A（推荐）**：不支持清空。按 6.1 直接拒绝空数组。用户想换扫描件就传新的覆盖旧的，
  想清空请找组委会走人工流程。前端保持现在的守卫。
- **方向 B**：支持清空，但**另开一个显式接口**（如 `DELETE /api/scan/files`），
  前端加「清空审核图」按钮 + 二次确认弹窗，绝不复用 `POST /api/scan/cau` 的空数组来表达这个意图。

### 6.5 附带提醒：后端现有测试把这个语义钉住了

[tests/test_files_scan_live.py:41-57](../../yilinbeihou/tests/test_files_scan_live.py#L41-L57)
的 `test_scan_upsert_ignores_supplied_user_id` 里：

```python
self.json_request("post", "/api/scan/cau", {"type": 1, "files": [{"id": 11}]})
...
self.assertEqual(scan.files, [{"id": 11}])   # ← 断言「整体替换」
```

对**非空**列表来说「整体替换」是合理语义，这个断言本身没问题，6.1 的改法也不会让它失败。
写在这里只是提醒：改接口时别只看这个测试绿不绿——它**覆盖不到空数组**这条路径。

## 附：一处没有成立、被我排除的怀疑

我一开始怀疑「重新上传后审核状态没有重置」——即已审核通过的记录被换掉扫描件后 `status` 还是「已通过」。
**这条不成立**，写在这里免得后端重复排查：

`status` 在整个后端**只有** `scan_create_update` 里那一处 `setattr` 能写，而前端三个调用点的 payload
都**不含** `status`（只发 `type` + `files`），因此 `if key in data` 为假、`status` 保持默认值 `0`。
全仓 grep `ScanFiles` 没有任何其他地方写 `status`。**也就是说审核状态这条链路目前整体是没接通的**，
属于另一件事（谁、什么时候把 `status` 置为「已审核」），不在本次报障范围内，但是个值得单独确认的问题。
