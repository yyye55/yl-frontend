- 确认库是空的，直接跑；或
- 用 `--fake-initial`（Django 会逐表探测后决定跳过还是执行），并在执行前**先备份**。

**G-1（阻断）**：见第四节。

### 1.5 旧审计报告的一处证伪

`yilinbei hou/docs/迁移审计报告.md` 的缺陷 1 称：迁移 `0004_auto_20260921_1138` 会对生产库执行 35 条 `ALTER COLUMN ... SET DEFAULT ' '`，是"真实 schema 变更"。

**实测证伪。** 探针 `.audit-probe/probe_0004.py` 直接调用 Django schema editor 的 `_field_should_be_altered` 判定后执行 `alter_field`：

```

```

**37 个 `AlterField` 全部产出 0 条 SQL。** 原因：这 37 个操作只改 `field.default`，而 **Django 从不在数据库层写 `DEFAULT`**——`default` 纯粹是 Python 侧的取值逻辑。因此：
- 该报告的缺陷 1 可以关闭；
- 但由此推出第二节的核心结论：**"NOT NULL 字段有空格默认值"这条要求，在当前实现下只对 Python 调用方有效，对数据库层无效。**

## 二、NOT NULL 字段的空格默认值

### 2.1 约定确实被广泛执行

逐字段枚举（`.audit-probe/probe_null.py`）结果：`core` 应用 19 张表、全部字段中，几乎所有 NOT NULL 文本列都带 `default=" "`，与用户要求一致。

### 2.2 但有三个 NOT NULL 文本列没有默认值

| 表.列 | 类型 | 说明 |
|---|---|---|
| `person.card` | `varchar(6)` NOT NULL | **有意为之**（卡号缺失不应伪装成空格），但意味着漏传即 `IntegrityError` |
| `report_draft.payload` | `text` NOT NULL | 草稿正文，理论上必传，但无兜底 |
| `users.password` | `varchar(128)` NOT NULL | Django `AbstractBaseUser` 固有，正常 |

### 2.3 核心风险：`default` 拦不住显式空串

**`field.default` 只在调用方"根本没传这个键"时生效。** 请求体里显式传 `""` 时，空串会原样写库。而高斯数据库在 A/ORA 兼容模式下**会把空串当 NULL 处理**，于是：

```
显式传 "" → 存进去变 NULL → 撞 NOT NULL → IntegrityError → 500
```

这与 SQLite/PostgreSQL 的行为**不同**（那里 `''` 就是 `''`，不撞 NOT NULL）。也就是说，这条风险**只在生产的高斯库上才会暴露**，本地和 CI 全绿也没用。

**已定位的具体触发点**：

| 位置 | 代码 | 风险 |
|---|---|---|
| `/api/ticket/make` | `phone=data.get("phone","")`、`ip=request.META.get("REMOTE_ADDR","")`、`name` 同 | `ticket_subscribe.phone/ip/name` 均 NOT NULL 无 DB 默认值 → 空串即 500 |
| `/api/file/create` | `Files.objects.create(..., **{k:v for k,v in data.items() if k in fields})` | `files.filename/type/url` 均 NOT NULL |
| `/api/live/` PUT | `Leader/Crew.objects.create(live_report_id=..., **values)` | `leader.name/card/phone`、`crew.name/card` 均 NOT NULL |

**建议**（交后端）：在 `services.py` 加一个统一的 `blank_to_space()` 归一化，在写入前把空串替换为 `" "`；或在高斯库侧为这些列补 DB 级 `DEFAULT ' '`。二者择一即可闭环，但**不能只靠 `field.default`**。

## 三、SQLite 专有语句

### 3.1 结论：隔离良好，无泄漏

全仓逐条扫描后，**唯一的 SQLite 专有 SQL** 位于迁移 `0009_report_person_conductor_instructor_rule` 的 `SQLITE_FORWARD` 常量——三条 `CREATE TRIGGER ... SELECT RAISE(ABORT, '...')`。该分支由 `_statements()` 内的 `vendor` 判断严格选择，**不会进入 PostgreSQL/GaussDB 轨道**。除此之外没有 `PRAGMA`、`AUTOINCREMENT`、`strftime`、`INSERT OR REPLACE` 之类的库内 SQL。

**判定：符合第 3 条要求。** SQLite 分支仅服务于本地测试库，保留是合理设计。

### 3.2 但要注意两处"测试通过 ≠ 生产行为一致"

这两点不是缺陷，是**测试盲区**，需在上线前用人工/脚本补验：

1. **触发时机语义不等价**。PostgreSQL 侧是 `CREATE CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED`（**提交时**才校验），SQLite 侧是普通触发器（**语句执行时**立即校验）。同一批数据在两边可能一个通过、一个报错。`0009` 校验的是"每个节目每条 position 只允许一名指挥/指导教师"，属业务强约束，建议上线后专门手工验一次。

2. **`select_for_update()` 在 SQLite 上是空操作**。草稿配额（`lock_user_slot`）和票务并发的正确性**在 SQLite 上完全测不出来**——没有行锁、没有并发。代码注释已自陈这一点。生产切到高斯后必须重新压一遍并发。

## 四、高斯数据库（PostgreSQL 9.2.4）兼容性

### 4.1 已导出并逐条核对的 DDL

完整输出见 `.audit-probe/sql_dump.txt`。**结论先行：迁移中用到的每一条 SQL 构造，在高斯 DWS 与 openGauss 上都是受支持的**（逐项核对见 §4.8），三个最著名的高斯坑（`ALTER SEQUENCE … RESTART`、聚合 `FILTER`、列存表触发器）本库**一处都没踩**（§4.9）。

**因此本节真正的高风险不在 SQL 语法，而在"分支判据"与"历史数据"上**——即 G-1（vendor 字面量）与 M-1（`card` 收窄撞脏数据）。

### 4.2 【阻断·条件性】G-1：vendor 字面量判据

这是本次检查发现的**首要上线风险**。涉及三处：

| 迁移 | 判据 | vendor 不匹配时的行为 |
|---|---|---|
| `0009_..._rule` | `if vendor not in ("postgresql","sqlite"): raise RuntimeError` | **迁移直接中止 → 部署失败** |
| `0007_card_relax_unique_and_notnull` / `0008_alter_person_card` | `if vendor == "postgresql":` 走显式 SQL，否则退回 `schema_editor.alter_field()` | 退回的那条路径正是这两支迁移**明确要规避**的路径（会触发 Django 的 `WITH ORDINALITY` 查询，见下） |
| `0007_db_comments` / `0010_update_type_comments` / 其他 `COMMENT ON` | `if vendor == "postgresql":` | **静默跳过**，不报错但注释丢失 |

而 `.env.example` 的原文是：

```
# Production GaussDB values. Set DB_ENGINE to the validated backend supplied by the vendor.
GAUSSDB_ENGINE=django.db.backends.postgresql
```

即**部署要求使用厂商提供的 backend 包**。如果该 backend 的 `DatabaseWrapper.vendor` 不是恰好等于字符串 `"postgresql"`（例如厂商标为 `"gaussdb"`、`"opengauss"`、`"dws"`），**第 0009 条迁移会抛 `RuntimeError` 让整个部署在第 6/9 步崩掉**。

#### 澄清进展：厂商 backend 的 vendor 值已查明，是一刀切的 `"gaussdb"`

核对 `requirements.txt`（全文 19 项）后确认：

```
Django==3.2.24
psycopg2-binary==2.9.9      ← 唯一的数据库驱动
```

**依赖清单里没有任何厂商 backend 包**。而查证华为及各方的 GaussDB Django backend 源码后，得到确定结论：

| backend | 来源 | `DatabaseWrapper.vendor` |
|---|---|---|
| `gaussdb-django` | **华为官方**（GitHub `HuaweiCloudDeveloper`，PyPI 同名，当前 5.2.1） | **`"gaussdb"`** |
| `django-gaussdb-backend` | 社区（`darkathena`，Gitee） | **`"gaussdb"`** |
| `django-opengauss-backend` | 社区（`vimiix`，PyPI v0.4.1） | 非 postgresql |

即：**只要用了任何一个高斯专用 backend，`vendor == "postgresql"` 就是 False，G-1 必然触发。**

#### 但本项目的情况很可能是安全的 —— 因为它是 **DWS**

这里有一个关键区分，直接决定结论：

- **GaussDB（集中式/OLTP）** —— 需要上面那些专用 backend，vendor 是 `"gaussdb"`；
- **GaussDB(DWS)（MPP 数仓）** —— 内核正是 **PostgreSQL 9.2.4**，这与你给出的"pgsql 9.2.4"完全吻合；而华为官方文档明确规定 DWS **可以用标准第三方库 `psycopg2` 直连**（DWS 管理指南 §6.7 "使用 Python 第三方库 psycopg2 连接集群"，`pip install python-psycopg2`，在 DWS 8.1.3+ 上以 psycopg 2.9.1 验证）。

**若目标确为 DWS**（"9.2.4"这个基线强烈指向 DWS），则：

- 部署走标准 `django.db.backends.postgresql` + `psycopg2` → **`vendor == "postgresql"`** → **G-1 不触发**，所有 PG 分支正常走；
- `requirements.txt` 里的 `psycopg2-binary==2.9.9` 与华为验证过的 2.9.1 同一大版本，**吻合**；
- `.env.example` 里"supplied by the vendor"的措辞就只是**冗余的占位说明**，不指向真实的厂商包。

| 情况 | vendor 取值 | G-1 是否触发 |
|---|---|---|
| **甲**：DWS + 标准 `django.db.backends.postgresql` + `psycopg2` | `"postgresql"` | **不触发**。G-1 可关闭 |
| **乙**：GaussDB 集中式 + 厂商 backend（`gaussdb-django` 等） | `"gaussdb"` | **触发**。`0009` 抛 `RuntimeError`，部署崩在第 6/9 步 |

**综合判断：情况甲的可能性明显更大**（`requirements.txt` 无厂商包、基线号 9.2.4 指向 DWS），但 `.env.example` 的措辞留有歧义。**一行命令即可定案**：

```bash
# 在生产 venv 中执行，直接看 vendor 的真实取值
python -c "import django,os; os.environ.setdefault('DJANGO_SETTINGS_MODULE','django_config.settings'); django.setup(); from django.db import connection; print(connection.vendor)"
```

或直接在部署日志里打印 `connection.vendor`（建议加进 `deploy.sh` 的 preflight）。

**无论甲乙，都建议做的加固**：把判据从"vendor 是什么"改成"vendor 不是什么"（见下方），这样即使将来换 backend 也不会静默走错分支。

**另有一条 DWS 专有注意事项**（来自华为文档同一节）：`psycopg2` 走 DWS 时**拿不到 CN Retry**——因为 psycopg2 会在语句前发 `BEGIN`，而 CN Retry 拒绝事务块内的语句；同时 `sslmode=verify-full` 不被支持。若生产依赖 CN Retry 做节点故障自动重试，需要知悉这一点。

**建议**（交后端）：把判据从"vendor 是什么"改成"vendor 不是什么"：

```python
# 建议改为按能力判断，而非按厂商名字判断
if connection.vendor == "sqlite":
    ...
else:   # 所有类 PostgreSQL 后端一律走 PG 分支
    ...
```

并在 `deploy.sh` 第 5/9 步之前**加一条 preflight 断言**，把实际 `connection.vendor` 打进部署日志。这样即使厂商 backend 命名不同也不会静默走错分支。

### 4.3 `WITH ORDINALITY` —— 为什么 0007/0008 要费那么大力气绕开

Django 3.2.24 的 PostgreSQL introspection（`django/db/backends/postgresql/introspection.py`）在 `get_constraints()` 里使用：

```sql
FROM unnest(c.conkey) WITH ORDINALITY cols(colid, arridx)
```

`WITH ORDINALITY` **是 PostgreSQL 9.4 才引入的**。9.2.4 基线上不支持。这条查询由 `_delete_composed_index()` / `_alter_field()` 内部触发——也就是说，**普通路径的 `alter_field` 一旦走到"删约束"，在高斯上就会报语法错**。

这正是 `0007`/`0008` 用 `SeparateDatabaseAndState` + 裸 `ALTER TABLE ... DROP CONSTRAINT IF EXISTS` 绕开的原因——**这个规避是正确的、必要的**。问题只在于它的触发条件是 `vendor == "postgresql"`（见 G-1）。**如果 G-1 被触发退回到 `alter_field`，就会正好踩中这条 9.4 才有的语法。** 两个风险是叠加的。

### 4.4 【高】M-1：`card` 收窄为 `varchar(6)` 的历史数据风险

`0008_card_last6_length` 执行：

```sql
ALTER TABLE "person"  ALTER COLUMN "card" TYPE varchar(6);
ALTER TABLE "crew"    ALTER COLUMN "card" TYPE varchar(6);
ALTER TABLE "leader"  ALTER COLUMN "card" TYPE varchar(6);
ALTER TABLE "ticket_subscribe" ALTER COLUMN "card" TYPE varchar(6);
ALTER TABLE "students" ALTER COLUMN "card" TYPE varchar(6);
```

在此之前，`0013_card_tail_identity` 的 `normalize_person_cards` 把 18 位身份证截成后 6 位。但它的处理是**不完整的**：对"既不是 18 位、也不是 6 位、也不是空"的值，**只打印警告，原值不动**。

**后果**：库中只要存在**一条**这样的脏数据（例如 15 位老身份证、或带空格的 18 位），`ALTER COLUMN ... TYPE varchar(6)` 就会因 `value too long for type character varying(6)` **硬失败**，部署停在第 6/9 步。

**上线前必须做的前置动作**（交后端/运维）：

```sql
-- 1. 先查有没有会撑爆的脏数据（五个表都要查）
SELECT id, card, length(card) FROM person
 WHERE card IS NOT NULL AND btrim(card) <> ''
   AND length(btrim(card)) NOT IN (6, 18);

-- 2. 若上面有结果，先人工确认这些是什么，再决定清洗方式
-- 3. 迁移顺序必须严格遵守 0008 文件头写的三步：
--    migrate core 0007_card_relax_unique_and_notnull
--    → 执行 normalize_person_cards
--    → migrate
```

### 4.5 【中】`logs.content` 上的 btree 索引仍被无条件创建

`0002_auto_20260916_2008` 发出：

```sql
CREATE INDEX "logs_content_db7ddd_idx" ON "logs" ("content");
```

而 `logs.content` 是 `varchar(5000)`。后端自己的《GAUSSDB_MIGRATION_ASSESSMENT.md》已把"在长文本上建 btree 索引"列为 **P0-2**，**但至今未实施**——本迁移仍是原样。高斯（DWS 系）对超长键值的 btree 索引有长度上限，且列存/MPP 场景下这类索引收益极低、写入代价高。

**建议**：确认后改为前缀索引或直接删除该索引（业务上 `logs` 几乎只按 `user_id`/`type`/时间范围查，内容全文检索需求未见）。

### 4.6 【中】varchar 的字节长度语义（P0-1，同样未实施）

同一份评估文档的 P0-1：高斯在部分兼容模式下按**字节**而非**字符**计算 `varchar(n)`。检查结论：

- `person.card` 收窄成 `varchar(6)` 后**不受影响**——卡号只允许 ASCII 数字与 `X`，6 字符 = 6 字节；
- 但 `report.choir_name`(255)、`person.name`(255)、`remark`(255)、`logs.content`(5000) 存中文时是 3 字节/字，**255 字节只够 85 个汉字**。姓名与团名通常够，但 `logs.content`(5000 字节 ≈ 1666 汉字) 和 `report.desc`(1000 字节 ≈ 333 汉字) **有溢出风险**。

**建议**：上线前用真实报名数据跑一遍长度分布，确认没有接近上限的值；否则需把这些列改为 `text`。

### 4.7 【中】G-2：settings.py 的 GaussDB 开关写错变量

```python
# django_config/settings.py
if os.getenv("GAUSSDB_HOST") and os.getenv("DB_ENGINE", "").lower().find("gauss") >= 0:
```

开关要求 `DB_ENGINE` 中含子串 `gauss`。而 `.env.example` 里：

```
DB_ENGINE=django.db.backends.postgresql          # ← 不含 "gauss"
GAUSSDB_ENGINE=django.db.backends.postgresql     # ← 这个变量没被读
```

**后果**：运维若照着 `.env.example` 填，`GAUSSDB_HOST` 填得再对，**整个 GaussDB 配置块也不会生效**，Django 会静默回落到 `DB_HOST`/`DB_PORT`（示例值是 `127.0.0.1:5432`）。表现是"连不上库"或**更糟——连到了本机另一个库**。

**建议**：把判据改为 `os.getenv("GAUSSDB_HOST")` 单独决定（有 GAUSSDB_HOST 就用 GaussDB 配置），并在启动日志里打印实际生效的 `ENGINE/HOST/PORT`。

### 4.8 高斯 SQL 特性矩阵（已核对完毕）

对高斯 DWS 与 openGauss 官方文档逐项核对，**迁移中用到的每一项 SQL 构造都是受支持的**——这一节是**好消息**，此前的担忧可以放下。

| # | 迁移依赖的构造 | 高斯 DWS | openGauss | 判定 |
|---|---|---|---|---|
| 1 | `CREATE CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED … FOR EACH ROW EXECUTE PROCEDURE` | 支持 | 支持 | ✅ |
| 2 | 普通 `CREATE TRIGGER … AFTER INSERT/UPDATE/DELETE` | 支持 | 支持 | ✅ |
| 3 | `CREATE OR REPLACE FUNCTION … RETURNS trigger … LANGUAGE plpgsql` | 支持 | 支持 | ✅ |
| 4 | `DO $$ … $$` 匿名块（`DECLARE`/`BEGIN`/`RAISE EXCEPTION`） | 支持，默认 plpgsql | 支持 | ✅ |
| 5 | `CREATE UNIQUE INDEX … WHERE …`（部分索引） | 支持（仅普通行存表） | 支持 | ✅ |
| 6 | `ALTER TABLE … DROP CONSTRAINT IF EXISTS` | 支持 | 支持 | ✅ |
| 7 | `ALTER COLUMN … TYPE varchar(6)` / `DROP NOT NULL` | 支持 | 支持 | ✅ |
| 8 | `COMMENT ON COLUMN` | 支持 | 支持 | ✅ |
| 9 | `pg_constraint` / `pg_attribute` / `'tbl'::regclass` / `array_length` / `ANY(conkey)` | 支持 | 支持 | ✅ |
| 10 | `count(CASE WHEN … THEN 1 END)`、`max(CASE WHEN … END)` | 支持 | 支持 | ✅ |
| 11 | `btrim(text)` | 支持 | 支持 | ✅ |

**DWS 的 `CREATE TRIGGER` 文档示例与 `0009` 的写法形状完全一致**（`CREATE OR REPLACE FUNCTION … RETURNS TRIGGER AS $$ … $$ LANGUAGE PLPGSQL;` 再加 `CREATE TRIGGER … EXECUTE PROCEDURE`）。官方对约束触发器的说明同样印证了 `0009` 的设计："约束触发器必须是 AFTER ROW 触发器"、"`DEFERRABLE` 仅作用于约束触发器"。

`0008` 的 `DO` 块所查的 `pg_constraint`，DWS 官方文档给出的示例就是同一形状：

```sql
SELECT conname FROM pg_constraint WHERE conrelid = 't1'::regclass AND contype = 'p';
```

且 `conkey` 在高斯上是 `smallint[]`（普通数组，与 PG 9.2 一致，**不是** `int2vector`），所以 `array_length(c.conkey, 1)` 与 `attnum = ANY (c.conkey)` 都是惯用写法，正是文档自己用的形式。

### 4.9 三处高危构造：本代码库**恰好都没用**（已逐条核查）

研究特别标出了三个高斯与 PostgreSQL 差异最大的高危点。逐一核查后确认**本代码库一处都没踩**：

| 高危构造 | 高斯上的行为 | 本库核查结果 |
|---|---|---|
| `ALTER SEQUENCE … RESTART [WITH] n` | **DWS 语法中根本不存在**（只支持 `MAXVALUE`/`OWNED BY`/`OWNER TO`）；openGauss 需 ≥6.0 | ✅ **全库零使用**（`grep ALTER SEQUENCE\|RESTART\|setval\|sqlsequencereset` 无结果） |
| 聚合 `FILTER (WHERE …)` 子句 | 文档未列出，与 9.2.4 基线一致（PG 9.4 才引入） | ✅ **全库零使用**（无 `aggregate(…, filter=Q(…))`） |
| 列存表上的触发器 / 部分索引 | 触发器**仅支持普通行存表**，列存/临时/unlogged 表上一律不可用 | ✅ 迁移未指定 `ORIENTATION`，默认即行存 |

第二项值得特别指出：**`0009` 用的是 `count(CASE WHEN position = 2 THEN 1 END)` 而不是 `count(*) FILTER (WHERE position = 2)`**——在 PG 9.2.4 基线上，前者是**唯一正确**的写法。这说明 `0009` 的作者对目标基线是清楚的，这个选择不是巧合。

> **运维注意**：上表第三项的前提是这些表保持**行存**。请勿对 `person`、`report_person`、`report_draft` 等表启用列存（`ORIENTATION=COLUMN`）——一旦启用，`0009` 的约束触发器与 `0006` 的两条部分唯一索引会直接失效或报错。

### 4.10 `SELECT … FOR UPDATE` 在 DWS 上会**报错**而非静默降级

这是研究给出的最需要注意的一条 DWS 专有行为：

> 对于 for update/share，执行计划不能下推的 SQL，**直接返回报错信息**
> 对列存表的查询不支持 for update/share

即：与 PostgreSQL 上"锁不住就降级"不同，DWS 上是**直接抛错**。全库 8 处 `select_for_update` 逐条核查后的结论是**风险较低**——全部是**单表 + 等值过滤**（`pk=`/`id=`/`user_id=`/`scope=`/`state=`/`report_id__isnull=`），**没有任何 JOIN**，因此不存在"计划下推不了"的情形：

| 位置 | 查询形状 | 评估 |
|---|---|---|
| `report_drafts.py:129` `lock_user_slot` | `User.all_objects…filter(pk=…)` | 单表，安全 |
| `report_drafts.py:456` 草稿暂存 | `ReportDraft…filter(user_id,scope,state,report_id__isnull)` | 单表，安全 |
| `views.py:1163/1222` 草稿提交/编辑 | 同上，多三个等值条件 | 单表，安全 |
| `views.py:1180/1216` 报名行锁 | `Report…filter(pk=…,user_id=…)` | 单表，安全 |
| `views.py:1394` 票务判重 | `TicketSubscribe…filter(ticket_id,card,name).exists()` | 单表；**但见下** |
| `views.py:1397` 票次锁 | `Ticket…filter(pk=…)` | 单表，安全 |

**但 `views.py:1394` 仍有一个与高斯无关的独立缺陷**（即 §5.3 的 S-2）：对**可能不存在的行**加锁等于没加锁，且这里用的是 `.exists()`——它不返回行、也就没有可锁定的行。这是竞态问题的根源，且**在 PostgreSQL 上同样存在**，不能归因于高斯。

**结论**：`FOR UPDATE` 在本库的形状下应当可用，但鉴于 DWS 是"报错而非降级"，上线前**应在真实集群上压一次草稿提交并发**（这同时也是 §3.2 提到的 SQLite 锁盲区）。

### 4.11 序列在 MPP 下的行为

`bigserial` 在高斯上受支持（`smallserial`/`serial`/`bigserial` 均在数据类型表中列出），`setval()`/`nextval()`/`currval()` 也都有文档。需要注意的业务含义是：**MPP 架构下序列不保证连续无洞**（并行插入会跳号），所以任何依赖"ID 连续"的逻辑都不成立。核查代码后**未发现此类依赖**——统计口径都用 `count()` 而非 `max(id)`。

### 4.12 `SELECT *` 系统表的隐患（当前未触发）

DWS 的 `pg_constraint` 比标准 PostgreSQL **多出 `consoft`、`conopt` 两列**。显式列名不受影响，但 `SELECT *` 或按位置取值会错位。核查 `0008`/`0007` 的 `DO` 块：**全部使用显式列名**（`c.conrelid`、`c.contype`、`a.attname`、`c.conkey`），未触发。记录在此供后续维护者注意。

### 5.2 【阻断】S-1：`/api/ticket/*` 是唯一无鉴权的路由，且泄露 PII

团队已经意识到这一点，但尚未动手。**建议在上线前完成摘除。**

### 5.3 【高】S-2：`/ticket/make` 的时间闸门已永久失效 + 并发竞态

**当前是 2026-09-29**，该条件恒为 False，即闸门**永久打开**。任何人可随时调用 `/ticket/make` 预约。

#### S-9 专项：导出范围判定本身没有问题，问题在它与类型改写叠加

**先说清事实，避免误判**。核对后，导出接口的数据范围**是有正确实现的**，不是漏洞：

```python
# apps/core/services.py:78
def export_report_scope(user):
    """市州端（type=1）导出归属于本市的各中小学账号报名；其余账号只导自己。"""
    if user.type == User.TYPE_CITY:
        return {"user_id__in": subordinate_school_ids(user)}
    return {"user_id": user.id}
```

`/export/report`、`/export/person`、`/export/data` 三个接口都正确地套用了它。而 `/admin/export/data1|data2`（`role_error(request, 3)` 后 `Report.objects.all()`）与 `/committee/export/data`（`role_error(request, 2)`）导的确实是**全量**数据——但这是**有意设计**，`views.py:882` 的 docstring 明确说明了"组委会需要全量导出"以及为什么要把两个数据范围分开。**这部分不作为缺陷计入。**

**真正的风险是两条已知问题的组合**：

```python
# apps/api/views.py:671  user_update_admin
setattr(user, "type", <来自请求体>)
user.set_password(RESET_PASSWORD_DEFAULT)
user.save()
```

`role_error` 是朴素的 `user.type != expected` 相等判断，**没有任何其他屏障**。因此：

> `user_update_admin` 允许把任意账号的 `type` 改写为 3 → 该账号随即通过 `role_error(request, 3)` → 调用 `/admin/export/data1` 拿到**全库报名与人员数据**。

也就是说，提权路径的终点不是"改个字段"，而是**完整导出全部公民个人信息**。这两条在既有安全报告里是分开列的两项，**叠加后的严重性没有被指出过**，建议后端按一条攻击链来处置。

**建议**：`user_update_admin` 必须禁止改写 `type`（或在改动 `type` 时要求二次鉴权与审计）；`role_error` 涉及的 `type` 值应改为只读、由后台管理流程设定。

## 六、数据流向与存储的精准性、严谨性

### 6.1 【高】D-1：`group_type` 字段不存在，「中学」统计恒为 0

```python
# apps/api/views.py:988
middle = Report.objects.filter(group="0", group_type=1, **report_filter).count() \
         if hasattr(Report, "group_type") else 0
```

核对 `apps/core/models.py`：**`Report` 模型没有 `group_type` 字段**。`hasattr` 恒为 False，因此 `middle` **恒为 0**。

函数 docstring 自称是"市州端/中小学端共用的 40% 口径面板"。后果：市州端和中小学端看到的**中学组报名数为 0**，而 40% 口径的基数因此被低估。这是**直接呈给主管部门看的统计数字**，属上线前必修。

**建议**：确认 40% 口径的准确定义后，用 `group="中学组"`（或 `group="0"` 配合其它判据）重写，并删除 `hasattr` 这种"字段不存在就静默返回 0"的写法——它把**字典错误变成了一个看起来合法的 0**。

### 6.2 【中】D-2：`report.group` 两套口径混存

同一个字段同时存在两种取值约定：

- **中文标签**：`"小学组"`、`"中学组"`、`"大学组"` —— 见 `views.py:512-513`、`952-959`
- **数字串**：`"0"`、`"1"`、`"2"`、`"3"` —— 见 `views.py:962-966`，且 `views.py:979` 的注释直接承认 `group="0"` 是"历史遗留的数字组别串"

不同代码路径各查各的，没有归一化层。风险：新建的报名数据写入哪种格式取决于入口路径，一旦写错，另一端就查不到（**且表现为"统计为 0"而不是报错**，与 D-1 一样属于静默失效）。

**建议**：确定唯一口径（建议中文标签），写一条数据迁移把数字串归一化，并在 `Report` 模型上把可选值固化为 `choices`。

### 6.3 其他数据流不严谨点

| 项 | 位置 | 说明 |
|---|---|---|
| 时间格式两套 | `services.py:43-52` `model_dict` 用 `value.isoformat(sep=" ")`（空格分隔、带 `+00:00`）；`report_drafts.py` 用 `isoformat()`（T 分隔） | 前端需要同时兼容两种格式；建议统一 |
| `attach_report_people` 永不删 Person | `services.py` | 每次更新报名是"软删旧链接 + bulk_create 新链接"，`Person` 表**只增不减**且无软删标记。历史身份证后 6 位会长期残留，与"不得留存"的合规要求可能冲突 |
| `report_person` 无外键 | 模型定义 | `person_id` 是裸 integer，不是 ForeignKey。**没有数据库级引用完整性**，`Package` 应用层写错即产生孤儿数据 |
| `live_report.report_id` 死链 | 模型定义 | 同样是裸 integer，且 `live_report` 与 `report` 之间没有约束维护 |
| 身份证只存后 6 位 | `0013_card_tail_identity` | 设计如此。但后 6 位**允许重复**（UNIQUE 已被 `0007` 解除），因此它**不是身份标识**。全系统必须确保所有按人员去重的逻辑用的是 `person_id` 而非 `card`——建议后端自查一遍 |
| `_dinner_counts` 固定 6 槽 | `services.py` | 用餐预约按固定 6 个时段对齐，若实际时段数变化需要同步改代码 |
| 时区 | `settings.py` | `USE_TZ=True` + `TIME_ZONE="Asia/Shanghai"`，DB 中存 UTC。导出给用户的文件里是 UTC 还是本地时间**需确认**——若直接输出 aware datetime，用户会看到比实际早 8 小时的时间 |

### 6.4 【中】D-4：前端限报口径文本过期，与后端不一致

后端 `apps/core/report_drafts.py:172-179` 的注释明确写着：

> 历史上 2026-09-23~27 曾短暂放开为「每组别 1 支、组别数不限」，**已收回**；
> `src/components/common/HaveToRead.vue` §二段 2 与本注释必须同步。

而前端 `src/components/common/HaveToRead.vue:58-64` 当前仍停留在**放宽版**：

> 红头文件原文是「每所学校限报一支队伍，且只能参加一个组别。」组委会后来放宽：
> 「每所学校每个组别限报一支队伍，小学组、中学组可各报一支（最多两支），大学组限报一支」

且该段落的结论时间戳标注为 **2026-09-22 / 09-23**，**没有体现 09-27 的收回**。

**实际差异**：后端现在的规则是"默认**总量 1**；只有管理员授予 `can_report_twice=True` 的学校才能报第二支，且每组别仍限 1"。前端文本却告诉所有学校"小学组、中学组可各报一支"——**会让学校以为可以报两支，实际提交时被拒**。

这条直接面向学校用户，属于上线前必须对齐的告知文本。**前端侧需按后端 09-27 口径改写**（提示文案用公文书面语）。

## 八、本次检查的验证方法与边界（可复现）
