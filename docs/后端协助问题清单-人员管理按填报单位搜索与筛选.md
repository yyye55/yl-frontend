**为什么右边已经有筛选框了还要这行**：甲方的原话是

右侧的筛选框是前端按他的需求 2 另做的入口，功能上是通的；
但用户会**先往搜索框里打字**，打完搜不到，报的还是同一个障。

### 这行改动安全吗（**实测过，不是推断**）

用**真实的 `Person` 模型**（`apps/core/models.py:252`）跑
**从 `views.py:600` 直接读出来的那行源码**（不是重打的副本），
内存 SQLite，7 条数据覆盖 `school` 为 正常值 / `NULL` / 空串 / 尾部带空格四种形态：

| keyword | 改前 | 改后 | 丢行 |
|---|---|---|---|
| `成都七中` | **0** | **3** | 无 |
| `七中` | 1 | 5 | 无 |
| `成都` | 0 | 4 | 无 |

穷举 10 个关键字，**丢行总数为 0**；`school` 为 `NULL` / 空串的行用姓名搜**仍能命中**。
生成的 SQL 就是三个 `LIKE` 的普通 `OR`：

```sql
WHERE name LIKE %k% OR card LIKE %k% OR school LIKE %k%
```

`NULL LIKE %k%` 求值为 `NULL`，该行只是不走 `school` 这一支 —— 但 `name` / `card` 两支照常命中，**不丢行**。
不改返回结构、不改分页语义；且该行只在 `if k:` 分支内，**不传 `keyword` 时根本不会执行**。

> 探针跑在 SQLite 上，生产是 Postgres。三值逻辑是标准 SQL，两边一致；
> 唯一差别是 Postgres 上 `icontains` 会渲染成 `UPPER(...) LIKE UPPER(...)`。

**一个数据侧的提醒（不是代码问题）**：`Person.school` 是各校在报名表里**手填**的自由文本。
若库里这一列大面积为空，那么即使改了这行，能搜到的也有限 —— 那属于数据质量，不是接口问题。

## 三、需求 B：新增 `school` 筛选参数（**✅ 已完成**）

> **状态：后端已实现**（提交 `00afaa4`，经 `2168e6f` 并入 `jy`），前端**已接上**（第六节）。
> 下面保留原始契约描述，作为前端调用与回归验收的依据；**后端无需再改本节**。

搜索框和筛选框是**两件事**：搜索是一个模糊词打三个字段，筛选是**只在单位上做限定**。
所以还需要一个独立参数。

### 3.1 契约

```
GET /api/admin/person/list?page=1&limit=10&keyword=&school=成都七中
```

| 参数 | 语义 | 缺省行为 |
|---|---|---|
| `school` | 对 `Person.school` 做 `icontains` 模糊过滤 | **不传或空串 → 行为与现在完全一致** |

- `keyword` 与 `school` **同时传 → 取交集**（先按 `keyword` 过三个字段，再按 `school` 限定单位）；
- `school` 用 `icontains`（模糊），**不是精确匹配** —— 理由见 3.3；
- 响应结构、分页信封（`{code,msg,data,count}`）**一律不变**，无需前端改动解析。

### 3.2 精确 patch

相对 `apps/api/views.py:599-600`（**仅存档；后端已按此实现，不必再改**）：

```python
    qs = Person.objects.all().order_by("id"); k = request.GET.get("keyword")
    if k: qs = qs.filter(Q(name__icontains=k) | Q(card__icontains=k) | Q(school__icontains=k))
    s = request.GET.get("school")
    if s: qs = qs.filter(school__icontains=s)
    return response(list_page(qs, request, model_dict))
```

第 4 行的 `if s:` 顺带兜住了 `school=`（空串是假值）的情况，不用额外判空。

### 3.3 为什么用 `icontains` 而不是精确匹配

`Person.school` 是**各校在报名表单的人员表里手填的自由文本**，不是外键、没有字典表。
同一所学校完全可能出现「成都七中」「成都市第七中学」「成都七中 」这类写法差异。
精确匹配会让筛选框稍差一个字就查不到人，反而像坏了。**模糊匹配更符合实际数据质量。**

> 如果后端希望改成精确匹配，请先告知：前端会改成下拉选择，那就需要先做第四节的单位清单接口。

## 七、后端改完之后我们怎么验

1. 用某个确实存在的单位名当 `keyword` 调 `/api/admin/person/list` → `count > 0`（需求 A）；
