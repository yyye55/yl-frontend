## 二、问题 1（阻塞）：暂存阶段不该要求 `position` / `type` 必填

### 现象

```
暂存校验：被拒  code=INVALID_DRAFT_PAYLOAD  person[0].position 必须是整数  None
```

### 触发路径（正常填表途中，不是异常操作）

1. 用户点人员表的「新增」—— `PersonTable.add()` 推的是**空对象** `{}`（`src/components/elementary/PersonTable.vue:350`）
2. 用户填了姓名，**还没选角色**
3. 此时该行的 `position` / `type` 是 `undefined`
4. 自动暂存（每 45 秒一次）触发 → `personToPayload` 输出 `position: null`
5. 后端 `_person()` 拒绝

### 原因

`apps/core/report_drafts.py:119`：

```python
def _person(item, index, complete=False):
    ...
    result["position"] = _integer(item.get("position"), "person[%s].position" % index, True, 0)
    result["type"] = _integer(item.get("type"), "person[%s].type" % index, True, 0)
    #                                                            ↑ required=True
```

而 `_integer`（同文件 `:101`）对 `required=True` 且值为 `None` 的处理是：

```python
def _integer(value, field, required=False, minimum=None):
    if value is None and not required:
        return None
    if isinstance(value, bool) or not isinstance(value, int):
        raise DraftError("%s 必须是整数" % field)     # ← None 落到这里
```

注意报错文案是「必须是整数」而不是「不能为空」，排查时会往类型问题上跑偏。

**`required` 应该只在 `complete=True`（提交）时生效。** 草稿按定义就是没填完的东西。

### 为什么前端不能绕过

前端只有两条路，两条都不能走：

- **不发这个键** —— 不行，`_person` 里 `item.get("position")` 仍是 `None`，照拒。
- **填个默认值 `position: 0`** —— 更糟。提交时 `_person(item, i, True)` 会拿这个假值当真值用，
  一个「用户还没分类」的人会被悄悄算成**正式队员**，直接进 `validatePersonCount` 的
  正式 35–65 人硬约束，红头文件的口径就破了。这是静默的数据污染，比报错难查得多。

### 建议改法

```python
result["position"] = _integer(item.get("position"), "person[%s].position" % index, complete, 0)
result["type"] = _integer(item.get("type"), "person[%s].type" % index, complete, 0)
```

即把 `True` 换成 `complete`。提交路径（`complete=True`）行为**完全不变**，
只有暂存阶段放宽。这个 `complete` 参数本来就是为这件事准备的，目前只用在
`name` / `card` 上（`:127`、`:128`）。

## 三、问题 2（轻微）：409 响应缺 `server_version`

`DraftConflict` 是带着服务端版本号抛出来的（`apps/core/report_drafts.py:40`）：

```python
raise DraftConflict("草稿已在其他页面更新", {"server_version": draft.version})
```

但 `_draft_error_response`（`apps/api/views.py:746`）**没有读 `error.data`**：

```python
def _draft_error_response(error):
    field = getattr(error, "field", None)
    data = {"code": getattr(error, "code", "INVALID_DRAFT_PAYLOAD"),
            "errors": [{"field": field, "message": str(error)}] if field else []}
    #        ↑ 这里从零重建，DraftConflict 传进来的 {"server_version": ...} 被丢掉了
    return response({"code": data["code"], "msg": str(error), "data": data},
                    getattr(error, "status", 400))
```

前端因此拿不到 `data.server_version`。**不影响功能**（冲突状态、停自动暂存、提示用户
点「重新加载服务器草稿」全都正常），只是提示少一半信息，用户不知道服务端是哪一版。

改法：把 `getattr(error, "data", None)` 并进 `data` 即可。

## 四、问题 3（轻微）：403 响应体没有 `code` / `msg`

`role_error`（`apps/api/views.py:66`）：

```python
def role_error(request, expected):
    if not user or user.type != expected:
        return response({"error": "无该页面操作权限！"}, 403)
```

响应用的是 `error` 键，没有 `code` 也没有 `msg`。前端归一后只能退到默认文案
「登录状态已失效，请重新登录」—— 而实际原因是**角色不对**，不是登录失效，用户会去重登
然后继续失败。建议补成与其他接口一致的 `{"code": ..., "msg": "无该页面操作权限！"}`。

## 五、问题 4（阻塞，前端已修）：键名 `person_id` → `id`

### 现象

```
暂存校验：被拒  code=INVALID_DRAFT_PAYLOAD  person[0] 存在不允许字段 {'fields': ['person_id']}
```

### 原因

`PERSON_FIELDS`（`apps/core/report_drafts.py:21`）里有 `id`，没有 `person_id`：

```python
PERSON_FIELDS = {"id", "name", "card", "age", "school", "phone", "gender",
                 "major", "head", "instrument", "other", "remark", "position", "type"}
```

而 `_person` 第一件事就是精确比对：

```python
unknown = set(item) - PERSON_FIELDS
if unknown:
    raise DraftError("person[%s] 存在不允许字段" % index, {"fields": sorted(unknown)})
```

**后果不是「字段被忽略」，是整份 payload 被拒** —— 只要报名表里有一个人
（报名表不可能没人），暂存和提交全部 400。**空表反而通过**，正好反证是这一个键的问题。

前端原本按规范原文发的 `person_id`。已在 `src/services/draftPayload.js` 改成 `id`
（两个方向：`personToPayload` 写出、`payloadToPerson` 读回），已提交 `6a2dc73`。

### 给后端的提醒

`_person` 这个「多一个键就 400」的严格策略本身是合理的（能及早暴露字段漂移），
但**报错信息只给了字段名、没给期望的字段列表**，排查时得去翻源码。
若方便，可在 `data.fields` 之外再带上 `allowed` 列表。

前端做了一条端到端探针，把**前端真实产出**的 payload 直接喂进**后端真实的**校验函数：

它会：用真的 `buildDraftPayload` 生成 4 个场景的 payload → 打印 json →

当前输出（问题 1 未修时）：

| 场景 | 暂存校验 | 提交校验 |

探针文件在前端的 `__debug__/`（已 gitignore），**后端仓库没有留下任何文件**，
跑完可以直接删。

## 七、已核对无误、不用再查的部分

以下是逐行对过的，**目前一致**，列出来是为了省掉重复核对：

- **scope 走路径**：`register_draft_routes("/school", 0, ...)` / `("/city", 1, ...)`，
  body 里前端不发 `scope` / `user_id` / `status` / `state` ✅
- **请求体形状**：POST 发 `{payload}`；PUT 发 `{version, payload}`；
  submit 发 `{version}`（不发 payload）；edit-draft 空 body ✅
- **body 解析**：前端发的 Content-Type 是 `application/x-www-form-urlencoded`
  但 body 是 JSON 文本（项目既有约定，为避开 CORS 预检）。后端 `parse_body`
  先 `json.loads(request.body)` 再退到 `request.POST`，**能正常解析，不用改** ✅
- **成功响应**：HTTP 200 + `code: 0`，`data` 里有 `draft_id` / `report_id` /
  `version` / `state` / `updated_at` ✅（`draft_data`，`report_drafts.py:263`）
- **`draft_id` / `report_id` 是字符串，`version` / `state` 是整数** ✅ —— 前端按此处理
- **submit 成功后没有 `draft_state` 键**（只有 `state`）：前端**不依赖**它，
  提交成功是自己置 `draftState = 1` 的，**不用改** ✅
- **edit-draft 路径**：走复数 `/reports/{id}/edit-draft`，与前端 `PATHS.editDraft` 一致，
  **原先担心的单复数不一致不存在** ✅
- **`group` / `establishment` 是 CharField 存中文**，后端 `_string` 要求字符串，
  前端发中文 ✅ —— 之前担心的「按规范示例发整数枚举」没有发生
- **文件槽位** `spectrum` / `file` 发的是数字字符串（如 `"35"`），
  `_entity_id` 要求 `isdigit()` 字符串 ✅
- **重复提交**：已提交的草稿返回 `code: 0` + `report_id`，前端按成功处理、复用
  `report_id`，不会重建报名 ✅
