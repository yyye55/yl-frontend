## 一、现象

### 1.1 用户报上来的原始报错

学生端（中小学端）点「提交」：

```
POST /api/primary/report/drafts/{draft_id}/submit
→ 400
{
  "code": "INVALID_DRAFT_PAYLOAD",
  "msg": "存在不允许字段",
  "data": {
    "code": "INVALID_DRAFT_PAYLOAD",
    "fields": ["dinner_reservation_counts"],
    "errors": []
  }
}
```

### 1.2 根因（三行）

1. 前端构建 payload 时**无条件**带上 `dinner_reservation_counts`；
2. 后端的白名单 `REPORT_FIELDS`（`apps/core/report_drafts.py:51-56`）里**没有这个键**；
3. 于是 `normalize_draft_payload`（`apps/core/report_drafts.py:279-281`）抛 `DraftError("存在不允许字段", {"fields": ["dinner_reservation_counts"]})`。

### 1.3 ⚠️ 影响面是「**提交全挂**」，不只是「暂存失败」

这一点最容易被低估，请务必看：

```python
# apps/core/report_drafts.py:306-307
def parse_submission_payload(raw, user_id, scope=None):
    value = normalize_draft_payload(raw)   # ← 提交路径的第一行就调它
```

**提交走的是同一道白名单。** 所以当前状态下：

- 所有暂存 → 400；
- 所有提交 → 400；
- **任何学校、任何渠道，一张报名表都交不上去。**

不是「用餐预约这个功能用不了」，是**整个报名系统写不进去**。

### 1.4 用户实际看到什么

`yl-frontend/src/api/reportDraft.js:186-188` 把 `INVALID_DRAFT_PAYLOAD` 归成 `INVALID`，`msg` **原样透传**。所以屏幕上就是那句：

> 存在不允许字段

对填表老师而言这是一句完全无法行动的话 —— 他们不知道是哪个字段、更不知道要改什么。

### 2.1 ⚠️ 一个容易误判的点：「6 格已经有了，所以只差人数」

`registration_form.py:158-181` 的 `_meal_cells()` 确实已经在渲染 6 个格子，但它是从**老字段** `dinner_reservation` 推出来的：

```python
def _meal_cells(report):
    """把 dinner_reservation（JSON 列表）填进 6 个用餐格。"""
    cells = [""] * len(MEALS)
    for item in _json_list(report.dinner_reservation):
        text = str(item).strip()
        if text.isdigit() and 0 <= int(text) < len(MEALS):
            cells[int(text)] = "√"        # ← 只打勾，没有人数
```

即：**「填在哪一格」已经能表达，但「几个人」没有地方存**。格子里只能是 `√`，不能是 `12`。
老字段的取值词汇是「下标数字 / 完整文案 / 简写」的**字符串集合**，语义上装不下一个整数人数。

所以这两件事是分开的，不能因为「导出看起来是 6 格」就认为字段已经就位。

## 三、字段规格（前端已在按这份发，请以它为准）

> 完整版在 [`用餐预约接口契约-第十二届.md`](./用餐预约接口契约-第十二届.md)。
> 下面是实现所需的全部内容。

### 3.1 名字与性质

- 字段名：**`dinner_reservation_counts`**
- 与老的 `dinner_reservation` **并存**，两者互不覆盖。
- 可选字段（老前端不传 = 零影响）。

### 3.2 下标映射（由后端定死，前端无权增删换序）

| 下标 | 时段 | | 下标 | 时段 |
|---|---|---|---|---|
| 0 | 11月20日午餐 | | 3 | 11月21日晚餐 |
| 1 | 11月20日晚餐 | | 4 | 11月22日午餐 |
| 2 | 11月21日午餐 | | 5 | 11月22日晚餐 |

前端对应实现：`yl-frontend/src/config/mealSlots.js`（唯一事实来源）。

### 3.3 取值

- 整个字段：`null` 或**数组**，长度 ≤ 6，不足由后端补 `null` 对齐。
- 元素：`null` 或 **≥ 0 的整数**。
- `counts[i] > 0` = 第 i 个时段订 N 人。
- `null` / `[]` / 元素 `null` / `0` 四者**语义等价**，都是「该时段未填人数」。

### 3.4 前端实际发出的形状（恒为长度 6 的数组）

```
[]                              → 后端收到 [null, null, null, null, null, null]
[null, null, 12, null, null, 8] → 21日午餐 12 人、22日晚餐 8 人
```

`buildDraftPayload` 里的 `normalizeMealCounts()`（`yl-frontend/src/services/draftPayload.js:191-197`）
保证元素**只可能是 `null` 或正整数** —— 前端**故意不产出 `0`**（理由见 3.5）。

### 3.5 ⚠️ 两条路径严格程度不同，前端按**严**的那条约束自己

前端产出的 payload 是**同一份**，既喂草稿链路又喂提交链路，而提交链路走的是
`normalize_draft_payload` —— 所以只能按严格口径来。

- **草稿 / 提交路径（严格）**：非数组、长度 > 6、元素为布尔 / 字符串 / 小数 / 负数 → **400**；
- **直传 create / update（宽松）**：数字字符串 `"12"` → `12`；布尔 / 负数 / 垃圾 → `null`；非数组整体视为未填；不报错。

### 4.1 A —— 模型加列（`apps/core/models.py`）

紧挨着 `dinner_reservation`（`:194`）加：

```python
    dinner_reservation_counts = LegacyJSONField(default=None, blank=True, null=True)
```

沿用 `LegacyJSONField` 与老字段同款（同一列族，物理类型仍是 TEXT，不需要 JSONB）。

**`default=None` 而不是 `default=list`，这是有具体依据的**，不是风格偏好 ——
`LegacyJSONField.to_python()`（`apps/core/models.py:32-34`）对空值的处理是：

```python
if value in (None, ""):
    return [] if self.default is list else value
```

即：`default=list`（老字段的写法）会把库里的 `NULL` **读成 `[]`**，于是「从来没填过」和
「填了但六格全空」在 Python 侧再也分不开；`default=None` 则原样返回 `None`，两者可区分。

对导出有用（`counts is None` → 整栏交回老字段；`counts == [None]*6` → 明确是「填过但都空」），
且**存量数据天然是 `NULL`，不需要任何回填**。前端两种都能吃（`normalizeMealCounts` 对
非数组一律当未填），所以这里纯看你们要不要保留这个区分度。

### 4.2 B —— 迁移（⚠️ 编号已被占用，别用契约文档里写的那个名字）

契约文档 §六 里写的是 `0014_report_dinner_reservation_counts` —— **那个编号已经用掉了**。

所以新迁移**必须** `dependencies = [("core", "0014_merge_0013_card_tail_0013_merge_twice")]`，

**如果按契约文档写的 `0014_...` 命名，会和现有的 `0014_merge_...` 构成两个同名编号的叶子**，
迁移图分叉 —— 这在 GaussDB 部署时是会在最坏的时刻炸的那种问题，请务必避开。

### 4.4 D —— 严格校验分支（`apps/core/report_drafts.py:283-298`）

⚠️ **这里是本次最容易踩的坑**：`normalize_draft_payload` 的循环是

```python
for field in REPORT_FIELDS - {"person"}:
    value = raw.get(field)
    if field in {"spectrum", "file"}: ...
    elif field == "time_length": ...
    elif field == "dinner_reservation": ...
    else:
        result[field] = _string(value, field, maximum=...)   # ← 默认分支
```

**只做 C 不做 D 的话**，新键会落进最后的 `else`，被 `_string()` 当成字符串，
于是 400 的文案从「存在不允许字段」变成 **「`dinner_reservation_counts` 必须是字符串」**
—— 报错换了，问题没解决，很容易被误判成「改好了但前端发错了」。

在 `elif field == "dinner_reservation":` 那一支后面插入：

```python
        elif field == "dinner_reservation_counts":
            # 复用餐房路径的整数校验：_integer 已拒绝 bool 与非 int，minimum=0 拒绝负数，
            # 值为 None 时返回 None（= 该时段未填，合法）
            if value is None:
                result[field] = None
            elif not isinstance(value, list):
                raise DraftError("dinner_reservation_counts 必须是数组")
            elif len(value) > MEAL_SLOT_COUNT:
                raise DraftError("dinner_reservation_counts 最多 %s 项（对应 6 个用餐时段）" % MEAL_SLOT_COUNT)
            else:
                counts = [_integer(item, "dinner_reservation_counts[%s]" % i, False, 0)
                          for i, item in enumerate(value)]
                result[field] = counts + [None] * (MEAL_SLOT_COUNT - len(counts))
```

`MEAL_SLOT_COUNT = len(MEALS)`，直接复用 `registration_form.MEALS`（已是 6 项），**不要再写一个字面量 6**。

**关于 `_integer`（`report_drafts.py:236-243`）为什么正好合用**：

- `isinstance(value, bool)` 已被显式排除（`:239`）—— 这一条很关键，Python 里 `True` 是 `int` 的子类，
  不排掉的话 `[true, false, ...]` 会被静默存成 `[1, 0, ...]`；
- `minimum=0` 拒绝负数；
- `required=False` 且值为 `None` 时返回 `None` —— **元素为 `null` 必须合法**，别传 `required=True`。

### 4.5 E —— 以下三处**自动生效，一行都不用改**（但请确认这是你要的语义）

| 位置 | 为什么自动 | ⚠️ 需要注意 |
|---|---|---|
| `payload_from_report()` `report_drafts.py:326-330` | 它是 `{field: getattr(report, field) for field in REPORT_FIELDS ...}`，加了 C 就自动回吐 | 无。这是「驳回 → 重编辑」链路，回吐是关键 |
| `create_report_from_submission()` `:361` / `update_rejected_report_from_submission()` `:378-379` | 前者 `Report.objects.create(**submission.report)`，后者 `setattr` 全量循环 | 无 |
| `report_dict()` `apps/core/services.py:299-315` | 走 `model_dict()`，它遍历 `obj._meta.fields`（`:46`）| 无。列表页 / 编辑页回显自动带上 |
| **直传** `views.py:143-145`（create）与 `:182-186`（update） | `payload` 是按 `Report._meta.fields` 过滤 `data` 得来的 | ⚠️ **见下** |

**关于直传路径的两点，请你们定夺（我们无法替你们判断）：**

1. **它是「原样写入」，不做归整。** 前端草稿链路永远发规范形状，所以走不到这里；
   但如果有别的客户端（或手工调接口）发 `"12"`、`true`、`-3`，会被**原样**塞进 JSON 列。
   契约 §4.1 承诺宽松路径要归一 —— 若要兑现，需要在两处各加一次归一调用。

2. **`update_report` 的「漏传是否清空」语义与老字段不同。**
   老字段在 `views.py:187-188` 是**无条件写**（`= data.get(...) or []`），所以漏传即清空；
   而新字段会落进 `:184-186` 的通用循环，**只在 `data` 里出现才 `setattr`**，漏传**不清空**。
   前端每次都全量发送该键，所以对我们无影响 —— 但契约 §4.1 末尾那句
   「`PUT /report/update` 漏传该键 = 清空」**对新字段并不成立**，将来会误导读代码的人，
   建议要么在代码里对齐、要么把那句注释改掉。

## 五、导出 / PDF（可选，但契约 §五 已承诺）

`_meal_cells()`（`registration_form.py:158-181`）当前只打 `√`。契约 §五 承诺的渲染规则是：

- `counts[i] > 0` → 格子印人数（PDF 印数字；Excel 写「11月20日午餐（12人）」），**优先于**老字段；
- `counts[i]` 为 `0` / `null` → 回退到 `dinner_reservation` 打 `√`；
- 只传人数也成立（`counts[i] > 0` 即视为订了该时段）；
- 老字段里无法归位的字符串，照旧并入备注。

**这一节可以晚于第四节单独上线**，不影响前端。但**不能只做第四节不做本节** ——
否则老师填的「12 人」会进库、却永远不出现在导出表上，是更难被发现的问题。

## 七、上线顺序（这次是反的，需要决定怎么收场）

### 7.1 前端这边有一个一行的紧急开关（**但代价要你们知情**）

`yl-frontend/src/services/draftPayload.js:102` 有一个同类先例：

```js
const SEND_DISPLAY_ORDER = true   // 「前端先上、后端还没上」窗口的一行回滚
```

它可以照搬成 `SEND_MEAL_COUNTS`，关掉后立即恢复提交。**但关掉 = 学生填的人数静默丢弃**：
用户填了数字、提交成功、以为订上餐了，实际没有。这比报错更难被发现，
所以**前端侧我们的建议是：除非确实等不及，不要用这个开关兜底，直接等后端**。

**如果你方能在短时间内上线第四个节的最小闭环（A+B+C+D），就不需要任何前端改动。**
请回一句大概时间，我们据此决定要不要启用开关。
